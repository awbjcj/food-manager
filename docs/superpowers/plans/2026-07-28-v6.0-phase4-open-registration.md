# v6.0 Phase 4 — Open Registration Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the single-id allowlist with open self-service registration, so any Telegram user can `/start` and get a working free-tier household — behind a kill switch, with the ban lever wired in.

**Architecture:** One function changes. `resolve_authorization()` in `app/handler_support.py` has been the single membership gate since v4.0, so opening the doors is an edit to its three branches plus a settings flag — not a refactor. `ALLOWED_TELEGRAM_USER_ID` is repurposed (operator identity, a role it already plays for `OwnerAlerter`) rather than removed.

**Tech Stack:** Python 3.12+, uv, aiogram 3.30, SQLModel, pytest, ruff.

**Spec:** `docs/superpowers/specs/2026-07-28-v6.0-multi-tenant-commercialization-design.md` §10

**Depends on:** Phases 1–3 complete and merged. This phase is deliberately last: metering bounds spend, billing collects money, and `/ban` exists — all three must be in place before strangers can register.

## Global Constraints

- Everything in Phase 1's Global Constraints still applies.
- **`OPEN_REGISTRATION` defaults to `false`.** Phase 4 ships the capability; flipping the flag is a separate, deliberate operational act (Task 5).
- **Banned users are rejected at the gate**, before any handler runs. That is why `Admission` has no `"banned"` reason — a banned user can never reach `admit()`.
- **`provision_solo_household` already creates a free `Subscription`** (Phase 1 Task 7), so no code path can produce a household without an entitlement.

## Deviation from the spec

`OPEN_REGISTRATION` is **not** in the spec's settings table (§17). It was added
while planning because §14 requires this phase to be independently shippable,
and without a flag "ship phase 4" and "open the doors to the public" would be
the same irreversible act. The flag makes the code deployable and the launch a
separate, reversible decision — see the go-live checklist in Task 5.

Replace `resolve_authorization`:

```python
def resolve_authorization(
    session: Session,
    *,
    allowed_user_id: int,
    telegram_user_id: int,
    open_registration: bool = False,
) -> AuthStatus:
    """The one membership gate.

    A ban is checked before anything else, so a banned user never reaches a
    handler - which is why the quota meter has no "banned" outcome.
    """
    existing = session.get(User, telegram_user_id)
    if existing is not None:
        if existing.banned:
            return AuthStatus(False, None, is_bootstrap=False)
        return AuthStatus(True, existing, is_bootstrap=False)
    if open_registration or telegram_user_id == allowed_user_id:
        # is_bootstrap now means "first contact, provision a household",
        # not "is the operator".
        return AuthStatus(True, None, is_bootstrap=True)
    return AuthStatus(False, None, is_bootstrap=False)
```

Update `authorize_and_get_user` to accept and forward `open_registration`, defaulting to the module flag:

```python
def authorize_and_get_user(
    session: Session,
    *,
    allowed_user_id: int,
    telegram_user_id: int,
    chat_id: int,
    chat_type: str,
    open_registration: bool | None = None,
) -> AuthDecision:
    status = resolve_authorization(
        session,
        allowed_user_id=allowed_user_id,
        telegram_user_id=telegram_user_id,
        open_registration=(
            OPEN_REGISTRATION if open_registration is None else open_registration
        ),
    )
    ...
```

Leave the rest of the function unchanged.
