# `/cook` v3.5 — Shopping List, Favorites & Feedback Recording

**Status:** Design approved, ready for implementation planning
**Date:** 2026-05-30
**Author:** awbjcj (with Claude)
**Builds on:** [`2026-05-30-recipe-recommendation-design.md`](2026-05-30-recipe-recommendation-design.md) (the v3 `/cook` pipeline)

## 1. Summary

v3.5 extends the v3 `/cook` recommendation feature with three **function** additions
(latency/cost are explicitly out of scope this release). It deliberately ships the
*safe, self-contained* utilities now and **records — but does not yet act on —**
cooking feedback, so the data needed for v3.6 learning accrues from day one and the
cold-start problem dissolves.

1. **Persistent shopping list** — an honest "to-buy" memo, separate from the pantry.
2. **Save & re-cook favorites** — snapshot a recommended dish and re-diff it against
   today's pantry on demand, with zero LLM calls.
3. **Feedback recording** — `👍 Liked` / `👎 Not for me` buttons that persist a verdict
   on the `CookSession`, with **no effect on recommendations yet**.

Everything stays native to the codebase: deterministic, unit-testable services with
injected `Session` and caller-supplied `now`/`today`, reusing the existing
inline-keyboard + `normalization.py` matching, and a single Alembic migration.

## 2. Goals

- Make the v3 display-only missing-ingredients list **actionable** without lying about
  what's in the pantry.
- Let the user **save** a dish they liked and recall it later, re-computing only the
  shopping gap against current stock.
- **Capture cooking outcomes** in a shape that the v3.6 learning loop can consume
  directly, proven by a forward-compatibility test.
- Add no new latency or cost to the `/cook` pipeline itself.

## 3. Non-goals (explicit; deferred)

- **Learning behavior** (affinity ranking term + deterministic steering summary) —
  fully designed (see §7) but **deferred to v3.6**. v3.5 records the signal only.
- Dish dedup / `/history` view.
- Receipt-ingest auto-clear of shopping-list entries (the only cross-module synergy;
  kept out to minimise blast radius — manual check-off only in v3.5).
- Latency or cost optimization of the pipeline.
- Recipe-DB API / RAG corpus (still deferred from v3).

## 4. User-facing surface

### Result card (extends v3)
The top-pick card gains a button row:

```
[👍 Liked] [👎 Not for me]
[★ Save]  [➕ Add missing to shopping list]
[Show alternatives]
```

- `👍 / 👎` set the cook's feedback verdict (idempotent; re-tap overwrites).
- `★ Save` snapshots the currently shown candidate into favorites.
- `➕ Add missing` writes the shown candidate's missing ingredients into the
  shopping list.

### New commands
- **`/shopping`** — list pending to-buy items; each has a check-off button. Empty
  state when nothing is pending.
- **`/favorites`** — list saved recipes; each has a "🍳 Cook this again" button that
  re-diffs against current pantry. Empty state when none saved.
- **`/stats`** — gains a "dishes cooked / liked" line (cooked-count = feedback-count).
- **`/help`** — mentions `/shopping` and `/favorites`.

## 5. Data model — one Alembic migration (`0006`)

### `CookSession` — new columns
| column | type | notes |
|---|---|---|
| `feedback` | str | enum `{none, liked, disliked}`, default `none` |
| `feedback_at` | Optional[datetime] | set when a verdict is recorded |

The chosen dish stays fully recoverable from the existing `candidates_json` +
`chosen_index`, so **no copy of the recipe is stored** for feedback. Finished cook
rows are already retained (v3 convention), so the history is durable.

### New table `ShoppingList`
| column | type | notes |
|---|---|---|
| `id` | Optional[int] PK | |
| `user_id` | int FK user.telegram_id, index | |
| `name_raw` | str | as shown to the user |
| `name_normalized` | str | via `normalization.normalize`; dedup key |
| `qty` | Optional[float] | carried from the recipe ingredient when present |
| `unit` | Optional[str] | |
| `added_at` | datetime | |
| `bought_at` | Optional[datetime] | set on check-off; row retained |

Dedup: skip an add when a **pending** (`bought_at is None`) row with the same
`(user_id, name_normalized)` already exists.

### New table `SavedRecipe`
| column | type | notes |
|---|---|---|
| `id` | Optional[int] PK | |
| `user_id` | int FK user.telegram_id, index | |
| `title` | str | |
| `cuisine` | str | |
| `source_url` | Optional[str] | |
| `ingredients_json` | str (JSON) | snapshot of `RecipeIngredient[]` |
| `method_gist` | str | |
| `saved_at` | datetime | |

A **point-in-time snapshot** of the candidate at save time — favorites must not drift
if the pantry or the LLM changes later. Dedup by `(user_id, title, source_url)`.

## 6. Feature mechanics

### 6.1 Shopping list
- `➕ Add missing` takes the shown candidate's missing-ingredient list — exactly the
  output of the existing `cook_logic.shopping_list(recipe_names, pantry_normalized)` —
  and inserts each as a `ShoppingList` row, skipping pending dupes.
- **Semantics:** the shopping list is a *to-buy memo*, never the pantry. Receipt-ingest
  remains the sole writer of `PantryItem`; when the user shops and photographs the
  receipt, items flow into the pantry through the existing path. The shopping list is
  not auto-cleared by ingest in v3.5 (manual check-off only).
- `/shopping` lists pending rows (`bought_at is None`); a check-off button sets
  `bought_at` (row retained, hidden from the default view).

### 6.2 Favorites
- `★ Save` reads `candidates_json[chosen_index]`, snapshots it into `SavedRecipe`
  (dedup on `(user, title, source_url)`; duplicate → "already saved").
- `/favorites` lists saved recipes. **"🍳 Cook this again"** reloads the saved recipe
  and re-runs `cook_logic.shopping_list` against **today's** pantry, rendering the card
  + a fresh missing-ingredients list. **Zero LLM calls.** If the pantry already has
  everything → "you have everything for this 🎉".

### 6.3 Feedback recording
- `👍 / 👎` set `CookSession.feedback` (+ `feedback_at`). Idempotent; a later tap
  overwrites the verdict. **No ranking or generation change** — this release only
  records.
- `/stats` reports cooked/liked counts derived from feedback rows.

## 7. Forward-compatibility contract for v3.6 (learning)

v3.6 will turn the recorded feedback into recommendation behavior using the
**hybrid** mechanism settled during design:

- A **deterministic affinity term** added to the existing blend
  (`cook_logic.blended_score`): `affinity` = weighted overlap of a candidate's
  **cuisine + ingredients** with the user's **liked** dishes, minus **disliked**
  (all-time counts). Disliked is a **soft negative inside the affinity term only** —
  never promoted to the hard `exclusions[]` filter. Proposed rebalance (tunable
  constants, conservative at first): `0.3·health + 0.3·expiry + 0.2·deliciousness +
  0.2·affinity`. Neutral affinity (e.g. `0.5`) until history exists (cold start).
- A **deterministic steering summary** — the *same* aggregate, rendered as a short
  capped string (e.g. `"Liked: chinese, garlic, tofu. Avoid-ish: olives."`) injected
  into the selection + recipe prompts. No extra LLM call, one source of truth.

**Contract v3.5 must satisfy:** for any cook with a non-`none` `feedback`, the tuple
`(cuisine, ingredients[], verdict)` is reconstructable from `feedback` +
`candidates_json[chosen_index]`. v3.5 ships a unit test asserting this reconstruction,
so the learning data is provably intact before any learning code exists.

## 8. Edge handling

| Case | Handling |
|---|---|
| Feedback / save / add-to-list on an expired or superseded `CookSession` | Friendly "session expired — start a new `/cook`." |
| Duplicate `★ Save` | Skip; reply "already saved." |
| Duplicate `➕ Add` (pending row exists) | Skip that item; report what was added vs already-listed. |
| Empty `/shopping` / `/favorites` | Friendly empty state. |
| "Cook this again" with a fully-stocked pantry | "You have everything 🎉" (empty shopping list). |
| Check off an already-bought item | No-op (idempotent). |

## 9. Testing

Service/pure-function tests with injected `now`/`today` (no `datetime.now()` inside
services), mirroring existing `tests/test_cook_*.py`:

- **Shopping list:** add-from-candidate, pending dedup, list pending, check-off sets
  `bought_at` and hides the row, idempotent re-check.
- **Favorites:** save snapshot, `(user, title, source_url)` dedup, list, and
  "cook this again" re-diff (reusing `cook_logic.shopping_list`), including the
  fully-stocked-pantry empty case.
- **Feedback:** set verdict, idempotent overwrite, guarded against expired/superseded
  sessions; `/stats` counts.
- **Renderer/bot:** new buttons render; callback handlers route to the right service.
- **v3.6 forward-compat:** reconstruct `(cuisine, ingredients, verdict)` from a
  fed-back session and assert completeness.

## 10. Provider / cost note

No new LLM stages. The `/cook` pipeline (3 stages + web search) is unchanged; all v3.5
additions are deterministic Python over the database. Per-cook cost is unaffected.
