# Food Manager v4.1 — Multi-Language Support

**Status:** Design approved (pending spec review)
**Date:** 2026-05-31
**Author:** brainstorming session (grill-me)

## Goal

Let each user switch the bot to their language (English, Chinese, French, Spanish)
so that **everything they see** — static UI chrome *and* LLM-generated content —
is rendered in that language.

## Core decisions (locked via grilling)

| Decision | Choice | Why |
|---|---|---|
| Scope | Full UI chrome **and** LLM content | A half-translated screen is jarring; user wants true localization. |
| Storage of LLM content | **Canonical English in the DB**; language is a render-time concern | Keeps `normalized_name`, `ShelfLifeCache`, and `/correct` dedup operating on stable English keys. A language switch is just a re-render — no DB rewrite. |
| Language set | **Fixed curated menu**: `en`, `zh`, `fr`, `es` | Makes a frozen, reviewable, testable static catalog viable with zero runtime cost. |
| Dynamic-name translation | **Lazy LLM translate + persistent cache**, English fallback | High reuse for food names; handles later switches and multi-user households uniformly. |
| Setting scope | **Per-user** (`User.lang`) | Mirrors `tz`/`digest_hour`. Two members of one household can read the shared pantry in different languages with zero conflict — a free payoff of canonical-English storage. |
| Render threading | **Approach A**: explicit `lang` param + pre-resolved name map; two-phase async-resolve-then-sync-render | Preserves the project's two conventions: pure/synchronous renderers and no global state. |

## Architecture

The screen contains two categories of text that need different mechanisms:

1. **Static UI chrome** — hardcoded English in `renderer.py` / `bot.py` (digest
   headers, item-line tails, button labels, `/help`, usage strings, stats labels).
   *Not* from the LLM. Handled by a frozen translation catalog.
2. **Dynamic LLM content** — item `raw_name`, recipe `title`/`cuisine`/`method_gist`,
   correction `rationale`. Persisted in the DB as canonical English. Handled by a
   lazy LLM-backed translation cache.

### The spine: two-phase render

Renderer functions are pure and synchronous; dynamic-name translation is async and
cache-backed. You cannot call an async translator from inside a sync `render_digest`.
Therefore:

- **Phase 1 (async, in handler/scheduler):** read `user.lang`; collect the dynamic
  strings about to be shown; resolve them via `translate_texts` (cache hit, or one
  batched LLM call on miss) into a `{english: translated}` map.
- **Phase 2 (sync, in renderer):** render using the sync static catalog `t(...)` plus
  the pre-resolved name map.

This keeps renderers pure and unit-testable, matching the codebase's explicit-injection,
deterministic-`today` ethos.

## Components

### 1. Static catalog — `app/i18n.py`

- `LANGS = ("en", "zh", "fr", "es")`, `DEFAULT_LANG = "en"`.
- `MESSAGES: dict[str, dict[str, str]]` keyed by stable message-id (e.g.
  `"digest.header.today"`). English mandatory for every key; other languages
  optional and **fall back to English** when absent.
- `t(key, lang, /, **kwargs) -> str`: look up `[key][lang]` → fall back to
  `[key]["en"]` → `.format(**kwargs)`. A missing/mismatched placeholder is guarded
  at runtime (try/except → English fallback) so a catalog typo can never crash a
  scheduled digest. Dev-time, the completeness test (see Testing) makes it loud.
- **Locale formatting tables** (also here): `MONTH_ABBR[lang]`, `WEEKDAY_ABBR[lang]`,
  and relative-day phrasing (`today`, `expired {n}d`, `{n}d`). These replace
  `_fmt_date`, the `weekday_short` tuple, and the urgency tails currently inline in
  `renderer.py`. Hand-rolled; no Babel dependency.

### 2. Dynamic-name translation — `app/translation_service.py` + new model

- **New table `NameTranslation`** — *global, not household-scoped*:
  `(lang, source_text)` → `translated_text`. A translation of a name is a language
  fact identical across households, so a shared table de-duplicates cost.
  `source_text` is the **actual displayed string** (`raw_name`, recipe `title`,
  `method_gist`) — not `normalized_name`, because we translate what is displayed,
  not the matching key. `source_text` is indexed.
- `async translate_texts(session, texts, *, lang, llm) -> dict[str, str]`:
  - `lang == "en"` → identity map; no DB, no LLM.
  - Dedupe → check cache → batch all misses into **one** LLM call (prompt:
    "translate these short grocery/recipe strings to {lang}, return a JSON array in
    the same order") → write cache → return `{english: translated}`.
  - **Any failure → identity (English) for misses, no cache write, warn-log.** Never
    blocks the caller; the 8am digest always sends.
- LLM access reuses the existing provider-selector pattern: a `TranslationLLMClient`
  Protocol with Anthropic/OpenAI implementations; cost computed via the existing
  `_cost_micros`.

### 3. Setting + command

- `User.lang: str = "en"` (mirrors `tz`/`digest_hour`). Additive Alembic migration,
  default `'en'` → existing users see **zero behavior change** until they opt in.
- `/lang` handler mirrors `on_tz`: no arg → show current language + supported menu;
  `/lang zh` → validate against `LANGS`, persist, **confirm in the newly selected
  language**. Registered in `build_dispatcher`; added to `/help`. `/start` and
  `/help` text themselves localized.

### 4. Renderer refactor (Approach A)

- Every public `render_*` gains `lang: str = "en"`; literals become `t(...)`;
  `CallbackButton` labels localized.
- Functions emitting dynamic names gain `names: Mapping[str, str] = {}` (empty →
  identity), applied to `raw_name`/`title`/`method_gist` before interpolation.
- Date/weekday/relative tails route through the §1 locale helpers.

### 5. Handler & scheduler wiring

- A small async helper in `bot.py` gathers the dynamic strings a handler is about to
  show, calls `translate_texts(..., lang=user.lang)`, then calls the pure renderer
  with `lang` + name map.
- `send_digest_once` does the same before `render_digest` — the batch path that pays
  the one-time translation burst, with English fallback if the translator is down.

### 6. Cook pipeline

- Recipe `title`/`cuisine`/`method_gist` stay **generated in English**
  (`RECIPE_SYSTEM_PROMPT` unchanged) and are translated on render via the same
  service. Accepted nuance: recipe prose is fairly unique, so `/cook` and
  `/favorites` get a lower cache-hit rate and most cook results pay ~1 translation
  call. Acceptable given `/cook` is already a multi-call interactive flow.

## Error handling & edge cases

- Translation failure → English fallback, no cache poisoning, warn-log; digest never
  blocked.
- Unknown/removed `lang` value in DB → fall back to English.
- Placeholder mismatch in catalog → runtime English fallback; dev-time completeness
  test fails loudly.
- Numbers stay Arabic numerals across all four languages; only month/weekday names
  and relative phrasing are localized.
- Telegram message length differs after translation; `DIGEST_CAP` (20) is unaffected.

## Testing

- **Default `lang="en"` + empty name map = identity**, so all existing renderer/bot
  tests pass unchanged.
- New tests:
  - Catalog completeness + placeholder-parity (every key resolves in every lang;
    same placeholders across languages).
  - `t()` fallback behavior.
  - `translation_service` with a `FakeTranslationLLM`: en identity, cache hit/miss,
    batching, failure → English fallback.
  - zh render smoke tests for digest / list / cook.
  - `/lang` command test.
- Add `FakeTranslationLLM` to `tests/fakes.py`.

## Scope boundaries (YAGNI — not in v4.1)

- Open-ended / arbitrary user-typed languages (architecture leaves room; deferred).
- Any DB rewrite or re-translation on switch.
- Localizing receipt-parsed canonical names at source (they stay canonical English).
- Surfacing translation cost in `/stats`.
- Translating the user's own `/add` free-text back to them.

## Rollout

Additive column defaulting to `en`; catalog ships English-complete plus zh/fr/es,
with English fallback for any gap. No migration of existing data, no behavior change
until a user runs `/lang`.
