# Food Manager v4.6 — Frozen Storage State & Shelf-Life Refinement

**Status:** Design approved (pending spec review)
**Date:** 2026-06-08
**Author:** brainstorming session (grill-me)
**Scope note:** First of three independent tracks brainstormed together. The other two —
**digest triage UX** (the ate/toss/snooze button overload) and **recipe recommendation
upgrade** — are deliberately deferred to their own specs. This track is sequenced first
because it is a data-model decision the other two must later reflect, and because fixing
frozen expiries shrinks the digest list that motivates the interface track.

## 1. Goal

Stop treating frozen food as fresh. A frozen chicken breast or a box of hash browns
should carry a months-long expiry, not a 2-day one, so that (a) the daily digest stops
nagging about food that is fine, and (b) freezing becomes a first-class **"rescue from
waste"** action instead of an invisible one.

The mechanism: make **frozen** an explicit storage state on each pantry item, separate
from its food category, and derive shelf life from *(food × state)* using authoritative
freezer-storage data.

## 2. The core reframe (why the obvious fix fails)

The naive fix — "make the LLM categorize frozen items better" — cannot work, because the
problem splits into two cases that behave completely differently:

- **Case A — bought already frozen** (ice cream, hash browns, frozen peas/fish/meals):
  the name usually signals it; the LLM *can* infer it at ingest.
- **Case B — bought fresh, frozen by you** (chicken, steak): **nothing on the receipt
  signals it.** The LLM can never infer it. Only the user knows, and only after they get
  home and put it in the freezer.

Case B *is* the complaint ("chicken/steak are frozen but treated as fresh"), and it is
structurally uninferrable. Therefore the feature **requires a user action**, not just a
smarter prompt. The design covers both cases: LLM hints for A, a one-tap button for B.

## 3. Core decisions (locked via grilling)

| Decision | Choice | Why |
|---|---|---|
| State model granularity | **Binary frozen flag** (`storage = "default" \| "frozen"`) | Every example given was about freezing — none about counter-vs-fridge. A full storage axis (counter/fridge/freezer/pantry) is YAGNI: more schema, more UI, and the LLM would have to guess a default location for every food. |
| Declaration mechanism | **LLM hints (Case A) + `❄️ Freeze` button (Case B)** | The LLM auto-marks unambiguous frozen-aisle buys; a per-item button handles the uninferrable fresh→frozen case. Covers both with minimal taps. |
| Frozen-duration source | **Vendored USDA FoodKeeper table + search fallback + cached default** | FoodKeeper is the authoritative, public-domain source for freezer-storage times. It is *static reference data*, so it is bundled as a lookup table — no live API, no latency, no key, no network failure on a button tap. The existing search client fills gaps; a cached default covers misses. |
| Thaw / reverse transition | **One-way (no thaw state)** | User thaws-and-cooks, not thaws-and-stores. A thaw state would be dead weight. Using a frozen item ends with the normal `[Ate]` action. |
| Expiry origin on freeze | **New `frozen_on` column**; invariant becomes `expires_on = (frozen_on or purchased_on) + shelf_life_days` | Keeps purchase history honest rather than overwriting `purchased_on`. Frozen-aware creation/freezing/correction paths use this origin; the fresh refine path skips frozen rows. |
| Legacy `category="frozen"` rows | **Left as-is; no lossy backfill** | Backfilling a row's true food category (meat? bakery?) from `category="frozen"` is guesswork. Old rows keep working; only new ingests use the split model. |
| Freeze button placement | **Digest action row now; interface track reworks layout later** | Freeze belongs exactly where `[Tossed]` is — on near-expiry items, as the waste-rescue alternative to tossing. Accepts a temporary 4-button row that the deferred interface track will redesign. |

## 4. Architecture

Two axes that were previously conflated into one `category` field are separated:

1. **Food category** (what it *is*): `meat`, `bakery`, `produce`, … — unchanged set,
   except the LLM no longer uses `frozen` as a category value for new items.
2. **Storage state** (how it's *kept*): `default` | `frozen` — new, orthogonal.

Shelf life is now a function of *(food, storage)*. The change touches:

- **the schema** (two additive columns),
- **the ingest LLM contract** (a new `frozen` boolean on each parsed item),
- **one new pure module** (`frozen_shelf_life.py`) that resolves a frozen duration,
- **one new callback verb** (`act:freeze`),
- **rendering** (a Freeze button in the digest, a `❄️` badge in `/list`).

The design needs almost no new infrastructure because three existing decisions already
accommodate it:

- `ShelfLifeCache` is keyed by `(household_id, normalized_name)`, so a frozen duration is
  just another row under a frozen key — **zero cache-schema change**.
- `normalize()` already **preserves** the word "frozen" (it strips marketing adjectives
  but keeps form/state words), so `"frozen chicken"` is naturally a distinct key from
  `"chicken"`.
- Frozen expiry recomputation is contained to item creation/freezing/correction paths.
  The fresh web-search refine path skips frozen rows so it cannot replace a frozen
  duration with a normal-storage estimate.

## 5. Data model — one Alembic migration (`0012`)

### `PantryItem` — new columns

| column | type | notes |
|---|---|---|
| `storage` | str, default `"default"` | enum `{default, frozen}`. Not indexed in v4.6 (no query filters on it yet). |
| `frozen_on` | Optional[date], default `NULL` | the day the item entered the freezer (ingest purchase date for Case A, today for Case B). |

Migration `0012`: add both columns, backfill `storage='default'`, `frozen_on=NULL`.
Existing `category='frozen'` rows are **not** rewritten. Like every prior migration this
is purely additive — existing users see zero behavior change until they freeze something.

### Model-level type additions (`app/models.py`)

- `Storage = Literal["default", "frozen"]`.
- Extend `ShelfLifeSource` with `"frozen_foodkeeper"`, `"frozen_llm"`, and
  `"frozen_default"` so a frozen item's provenance is explicit in `/correct` diffs
  and debugging.

### Expiry invariant (changed)

```
expires_on = (frozen_on or purchased_on) + timedelta(days=shelf_life_days)
```

Applied wherever frozen rows are created, frozen, or corrected. For all non-frozen
items `frozen_on is None`, so the expression is byte-identical to today's behavior.

## 6. Ingest path — Case A (bought already frozen)

### LLM contract (`app/llm.py`)

- `ParsedItem` gains `frozen: bool = False`.
- `SYSTEM_PROMPT` updated: `category` always carries the **real food type** (meat,
  bakery, seafood, …); a new instruction sets `frozen: true` **only** for unambiguous
  frozen-aisle items (ice cream, frozen vegetables/fruit, frozen fish/meat sold frozen,
  frozen prepared meals, hash browns). When unsure → `frozen: false`. The word `frozen`
  is removed from the guidance as a *category* value for new parses (it remains in the
  `Category` Literal for back-compat with stored rows and `/correct`).

### Ingest behavior (`app/ingest_service.py`)

When `parsed.frozen` is true:
- resolve the frozen duration via §7 (`resolve_frozen_days(...)`),
- set `storage="frozen"`, `frozen_on=purchase_date`,
  `shelf_life_days=frozen_days`, `expires_on=purchase_date + frozen_days`,
- `shelf_life_source` / `ingest_shelf_life_source` map from the resolver's source:
  cache hit → `"cache"`; otherwise `"frozen_foodkeeper"`, `"frozen_llm"`, or
  `"frozen_default"` (mirroring how fresh ingest maps `cache_was_hit → "cache"`).

When `parsed.frozen` is false → unchanged from today.

## 7. Frozen-duration resolver — new module `app/frozen_shelf_life.py`

A pure, deterministic resolver (search client injected, mirroring the existing
web-search shelf-life refinement path):

```
resolve_frozen_days(session, *, household_id, food_name, normalized_name, search=None) -> FrozenDecision
```

Resolution order (cache key is **always** `_frozen_key(normalized_name) = "frozen " +
normalized_name`, uniformly for Case A and Case B — this never collides with the fresh
entry for the same food, and removes any "is this food inherently frozen?" judgment. The
FoodKeeper table is keyed by the **plain** food name; only the cache uses the prefix):

1. **Cache** — look up `ShelfLifeCache` under `_frozen_key(normalized_name)`.
   Hit → `source="cache"`.
2. **Vendored FoodKeeper table** — a static `dict[str, int]` of freezer-storage days,
   mapped from the USDA FoodKeeper public-domain dataset (e.g. chicken≈270, ground
   beef≈120, steak≈300, bread≈90, ice cream≈60, frozen vegetables≈300). Lookup is by
   normalized food, with the same conservative spirit as `shelf_life_defaults.py`.
   Hit → `source="frozen_foodkeeper"`, written back to cache.
3. **Search fallback** — reuse the existing `ShelfLifeSearchClient` with the query
   `"frozen <food>"`; cache under the frozen key. `source="frozen_llm"`.
4. **Conservative default** — any search miss/unavailability uses and caches a flat
   default (90 days). `source="frozen_default"`, so a freeze tap never errors.

`FrozenDecision` mirrors `ShelfLifeDecision` (`days`, `source`, `cache_was_hit`).

> **Vendoring note:** the FoodKeeper dataset is a U.S. government work (public domain).
> v4.6 vendors a curated subset as a Python literal — no runtime dependency, no network.
> The table lives next to `shelf_life_defaults.py` and is expanded the same way (`/correct`
> learns the rest over time, now under frozen keys).

## 8. Freeze action — Case B (you freeze fresh food)

### Surface

- New button `[❄️ Freeze]`, callback `act:freeze:<item_id>`, parsed by the existing
  `commands.py` action parser alongside `ate`/`toss`/`snooze2`.
- Appears in the **digest action row** on active items (the waste-rescue slot next to
  `[Tossed]`), via `build_digest_keyboard`.

### Service (`app/pantry_service.py`)

```
freeze_item(session, *, household_id, item_id, today, search=None) -> MutationResult
```

- Loads the owned item (`_load_owned`); if `status != "active"` or already
  `storage="frozen"` → `MutationResult(applied=False, was_already=True)` (idempotent).
- Resolves frozen days via §7, then sets `storage="frozen"`, `frozen_on=today`,
  `shelf_life_days=frozen_days`, `shelf_life_source` mapped from the resolver source
  (cache hit → `"cache"`, else `"frozen_foodkeeper"`/`"frozen_llm"`/`"frozen_default"`),
  `expires_on=today + frozen_days`, clears `snoozed_until`.
- Commits. Because the new expiry is far out, the item leaves the 7-day digest window on
  the next render — it stops appearing in the daily digest automatically.

> Note: unlike the other `act:` verbs, freeze may use the search fallback, so the callback
> handler passes the existing `ShelfLifeSearchClient` through. The §7 conservative default
> guarantees the tap still succeeds if search is unavailable.

## 9. Rendering (`app/renderer.py`, `app/i18n.py`)

- **Digest:** `build_digest_keyboard` adds `[❄️ Freeze]` to each item's row. *Accepted
  coupling:* the row is now four buttons (`Ate / Tossed / Snooze / Freeze`); the deferred
  interface track owns the final layout. New catalog key `btn.freeze`.
- **`/list`:** `render_item_line` / `render_list` prefix a frozen item with a `❄️` badge
  so the freezer's contents are visible at a glance. Read-only — no button, since freezing
  is one-way.
- **Self-healing clutter (the cross-track payoff):** frozen items get long expiries, fall
  outside the 7-day `list_digest_due` window, and disappear from the daily digest with no
  extra logic — directly shrinking the button wall that motivates the interface track.
- **i18n:** all new chrome (`btn.freeze`, any frozen-state labels) added across
  `en|zh|fr|es`; English values byte-identical-safe; placeholder-parity test still passes.

## 10. Edge handling

| Case | Handling |
|---|---|
| Freeze an already-frozen item | Idempotent no-op (`was_already=True`); friendly callback answer. |
| Freeze a non-active (eaten/tossed/removed) item | No-op; "that item isn't active." |
| Search unavailable during a freeze tap | Resolver returns the conservative flat default; tap still succeeds. |
| Item born frozen at ingest (Case A) | `frozen_on = purchase_date`; expiry from purchase date, not "today". |
| `/correct` on a frozen item | Uses the same `(frozen_on or purchased_on)` invariant; a user-supplied day count recomputes from `frozen_on`. |
| Legacy `category="frozen"` row | Untouched; `storage` stays `default`; no badge, no behavior change. |
| FoodKeeper miss **and** search miss | Conservative flat default (90d); cached so it's asked once. |
| Frozen item accidentally reaches fresh refine | Skipped; fresh web-search refinement does not update frozen rows. |

## 11. Testing

Service / pure-function tests with injected `today` and fake LLM/search clients (no
`datetime.now()` inside services), mirroring existing `tests/test_*` patterns:

- **Resolver:** cache hit; FoodKeeper hit; search fallback (+ cache write under the frozen
  key); search miss/unavailable → cached conservative default.
- **Freeze service:** recomputes `expires_on` from `frozen_on=today`; idempotent on an
  already-frozen item; rejected on non-active items; clears snooze.
- **Invariant:** `(frozen_on or purchased_on) + shelf_life_days` holds for fresh and
  frozen items; a fresh item is byte-identical to current behavior.
- **Ingest Case A:** `frozen=True` → `storage="frozen"`, `frozen_on=purchase_date`,
  long expiry, correct source.
- **Digest interaction:** a frozen item with a far expiry is absent from
  `list_digest_due`; an active near-expiry item's digest row includes the Freeze button.
- **Render:** `/list` shows the `❄️` badge for frozen items; existing English strings
  unchanged.
- **Fresh refine guard:** frozen items are skipped if they accidentally reach the
  normal-storage web-search refine path.
- **i18n:** catalog completeness + placeholder parity for the new keys.

## 12. Scope boundaries (YAGNI — not in v4.6)

- No thaw state / reverse transition.
- No counter/fridge/pantry storage axis (frozen only).
- No live food-science API (FoodKeeper is vendored static data).
- No backfill/remap of legacy `category="frozen"` rows.
- No change to `track_worthy` shelf-stable exclusion.
- **No digest button-overload redesign** — that is the separate interface track; v4.6 only
  adds the single Freeze verb to the existing row.
- No `/stats` surfacing of frozen counts or FoodKeeper hit-rate.

## 13. Rollout

Additive migration (`0012`) with safe defaults; existing rows become
`storage='default'`, `frozen_on=NULL` and behave exactly as before. The ingest prompt
gains an additive `frozen` field (defaulting false). No data migration, no behavior change
until the LLM flags a frozen-aisle item or a user taps `❄️ Freeze`.
