# Food Manager v4.8 — Pantry Action Interface (Digest Drill-Down)

**Status:** Design approved (pending spec review)
**Date:** 2026-06-09
**Author:** brainstorming session (grill-me)
**Lineage:** This is the **digest triage UX** track deferred by the v4.6 frozen-storage
spec (`2026-06-08-v4.6-frozen-storage-state-design.md` §12). The companion **recipe
recommendation upgrade** remains a separate, later spec.

## 1. Goal

Kill *selection ambiguity* in the daily digest. Today, when many items are due,
`build_digest_keyboard` renders one identical, unlabeled `[Ate][Tossed][Remind +2d]
[❄️ Freeze]` row **per item** (up to `DIGEST_CAP = 20` items → up to 80 buttons stacked
vertically). The buttons carry no item name, so acting on the right item means mentally
mapping a button row to the text line above it. With tens of near-expiry items this is the
core ergonomic failure.

Replace the per-item button wall with **labeled item-buttons** that drill into a
**single-item action card**. Every button names its item; every action lives on a roomy
card instead of a cramped shared row.

## 2. The core reframe

The fix is not "fewer buttons" or "smarter triage" — it is **making each tap target
self-identifying**. The digest already restricts itself to items expiring within 7 days
(`list_digest_due`), so volume is intrinsic to a full fridge; we cannot prune our way out.
Instead we change the interaction from *one-shot act-in-place* to *select-then-act*:

1. **List view** — the same digest text, but the keyboard is one labeled button per item.
2. **Item card** — tap an item → the message becomes a card for just that item, with its
   actions as large, unambiguous buttons.

This trades **one extra tap per action** for **never hitting the wrong item**. It is a
renderer + callback-routing change with almost no new domain logic: every underlying
action already exists (`mark_eaten`, `mark_tossed`, `mark_removed`, `snooze_item`,
`freeze_item`, `correct_item`, `propose_correct`). We re-shape *how they are reached*.

## 3. Core decisions (locked via grilling)

| Decision | Choice | Why |
|---|---|---|
| Interaction model | **Select-then-act drill-down** | Labeled item-buttons end the row-mapping guesswork and scale to tens of items. Rejected: one-tap triage (still ambiguous when many items are simultaneously near-expiry) and verb-first batch select (heavier multi-select state for a single-user-dominant workflow). |
| Volume handling | **Shared cap + `Show all N »` expand** | The existing `DIGEST_CAP` governs **both** the text lines and the item-buttons so they stay 1:1; `Show all` expands both together. Retuned to ≈10 for the button era. Reuses the `show:all` pattern; no per-page callback state. Most-urgent items win the capped slots. Rejected: true Prev/Next pagination (page-state callbacks for marginal benefit at this scale). |
| Item-button label | **icon + `#id` + name, 2 per row** (`🔴 #7 milk`) | The `#id` disambiguates duplicate names (two `milk` items stay distinct) and ties each button to its text line. 2/row stays compact for the expanded view. Long names may truncate — acceptable. |
| Card action set | **Ate / Tossed / +2d / Freeze / Correct / Remove / Back** | Parity with today's four actions **plus** Remove and Correct, which the card's extra room finally affords. Freeze hidden when the item is already frozen. |
| Snooze on card | **Single `+2d`** (unchanged) | Multi-duration snooze was explicitly *not* chosen; keep the hardwired `snooze_item(days=2)`. |
| Correct mechanism | **Quick nudges + `💬 Something else…` free-text** | Nudges (`+1w / +3d / −3d / use by today`) call `correct_item(days)` directly — no text, no LLM — and cover the common "wrong date" case. `Something else…` opens a free-text path for name/category/expiry via the existing LLM `propose_correct` flow. |
| Free-text capture | **Stateless `ForceReply`** | No FSM/conversational state exists in the codebase and none is added. The prompt embeds the item id; the reply handler parses it back out of `reply_to_message`. |
| Remove safety | **Confirm Remove only** | Remove is the only "this shouldn't exist" action and has no UI undo. One guard tap. Ate/Tossed/Snooze/Freeze/Correct stay single-tap. |
| Reach | **Digest-only (v1)** | `/list` stays read-only. The card + callback machinery is reusable, so extending to `/list` later is cheap. The "freeze-early" gap (Freeze only on near-expiry items) is knowingly deferred. |
| Message model | **Single message, edited in place** | List ⇄ card ⇄ sub-flows all `edit_text` + `reply_markup` on the one message, mirroring `_refresh_digest_message` and the cook flow's `_safe_edit_cb`. |

## 4. Architecture

The change is concentrated in two files:

- **`app/renderer.py`** (pure, synchronous): new card/menu renderers and keyboard builders;
  `build_digest_keyboard` re-shaped from per-item action rows to per-item *open* buttons.
- **`app/bot.py`**: a new `item:*` callback router for the drill-down states, plus one new
  reply handler for free-text Correct. Existing `act:*` handlers are reused (the verbs move
  from the digest keyboard onto the card).

No schema change. No migration. No new service functions — only new callers of existing
ones. `app/commands.py` gains parsing for the new callback verbs.

Reused building blocks (unchanged):

- `list_digest_due` / `render_digest` — the bucketed list text is **identical**; only the
  attached keyboard changes.
- `mark_eaten` / `mark_tossed` / `mark_removed` / `snooze_item` / `freeze_item` /
  `correct_item` — the action services.
- `propose_correct` → `render_correction_diff` → `build_apply_cancel_keyboard` → pending
  store — the entire free-text correction pipeline.
- The existing `NotOwnerOrMissing` / "already updated" guards for concurrency.

## 5. The three message states

All three are the **same** Telegram message, edited in place.

### 5.1 List view (the digest)

Text: unchanged — `render_digest` buckets (Expired / Today / Tomorrow / This week), each
line `🔴 ❄️ #3 spinach - 2d ago` as today.

Keyboard: **labeled item-buttons**, icon + `#id` + name, 2 per row, ordered by urgency
(expired first, matching the text order). Text lines and buttons share one cap
(`DIGEST_CAP`, retuned to ≈10) so they stay 1:1 — every visible line has its button. If
more items are due, a trailing `Show all N »` button (`show:all`) re-renders **both** the
text and the keyboard with all due items.

```
🍳 Tue Jun 9   (12 items)

Expired (2)
  🔴 #3 spinach - 2d ago
  🔴 #7 milk - 1d ago
Today (1)
  🟡 #12 chicken - today
…

[🔴 #3 spinach ][🔴 #7 milk   ]
[🟡 #12 chicken][🟡 #9 milk   ]
[🟢 #20 yogurt ][ Show all 28 »]
```

### 5.2 Item card

Tapping `item:open:<id>` re-renders the message as a single-item card.

```
#3 spinach — expired 2d ago

[✅ Ate]      [🗑 Tossed]
[⏰ +2d]      [❄️ Freeze]
[✏️ Correct]  [❌ Remove]
[⬅ Back to list]
```

- Card text shows the item's name, id, qty/unit, urgency phrase, and `❄️` if frozen.
- `❄️ Freeze` is **omitted** when `storage == "frozen"` (freezing is one-way).
- Ate / Tossed / +2d / Freeze act, then return to the refreshed **list view**.
- Correct → the correct sub-menu (§5.3). Remove → the remove confirm (§5.4).
- Back → list view (capped; expansion state is not remembered in v1).

### 5.3 Correct sub-menu

```
✏️ Correct #3 spinach
shelf life 7d · expires Jun 9

[+1w longer][+3d longer]
[−3d shorter][use by today]
[💬 Something else…]
[⬅ Back]
```

- Each nudge calls `correct_item(days=…)` (§6), then **re-renders this card/menu** with the
  updated expiry so the effect is visible; the user can nudge again or go Back.
- `💬 Something else…` starts the free-text correct flow (§7).
- Back → item card.

### 5.4 Remove confirm

```
Remove #3 spinach?
This can't be undone here.

[✅ Yes, remove][⬅ Cancel]
```

- Yes → `mark_removed`, return to refreshed list view.
- Cancel → item card.

## 6. Nudge semantics

Nudges map to the existing `correct_item(session, *, household_id, item_id, days, today)`,
which recomputes `expires_on = (frozen_on or purchased_on) + days` and writes a user
correction to `ShelfLifeCache`. Let `origin = frozen_on or purchased_on` and `cur =
shelf_life_days`. Results are clamped to `[SHELF_LIFE_DAYS_MIN, SHELF_LIFE_DAYS_MAX] =
[1, 730]`.

| Button | callback code | new `days` |
|---|---|---|
| `+1w longer` | `p7` | `cur + 7` |
| `+3d longer` | `p3` | `cur + 3` |
| `−3d shorter` | `m3` | `max(1, cur − 3)` |
| `use by today` | `today` | `max(1, (today − origin).days)` |

**Documented edge:** `use by today` cannot produce an expiry *before* `origin + 1`, so for
an item whose `origin` is today it yields tomorrow, not today (the `days ≥ 1` floor). Digest
items are near-expiry with `origin` in the past, so this is a corner case, not the norm.

Because nudges reuse `correct_item`, they inherit its cache-learning side effect: the
corrected shelf life is written under the item's storage-aware cache key, so the household
learns the right duration for that food.

## 7. Free-text Correct — stateless reply capture (the one new mechanism)

No FSM is introduced. The flow is fully stateless via Telegram's `reply_to_message`:

1. `💬 Something else…` (`item:ctext:<id>`) sends a **new** message carrying a `ForceReply`
   markup and an embedded, parseable id token, e.g.
   `✏️ Reply to this message with the fix for #3 spinach — e.g. "lasts 2 weeks" or "it's
   whole milk".` The list/card message is left intact.
2. A new aiogram message handler matches messages whose `reply_to_message` is one of our
   correct prompts (detected by a stable marker/prefix in the prompt text). It parses the
   `#<id>` back out of `reply_to_message.text`, loads the owned item, and calls the existing
   `propose_correct(...)`.
3. From there the **existing** pipeline runs unchanged: `render_correction_diff` +
   `build_apply_cancel_keyboard`, a `PendingCorrection` row, and Apply/Cancel → `apply_correct`
   / terminal state. On Apply, the usual `render_applied_correction` message is shown.

This branch lives in its own message thread (the ForceReply prompt and its diff), so it does
not entangle the in-place list/card editing. The typed `/correct <id> <free text>` command
is untouched and remains a second entry point to the same `propose_correct` pipeline.

If id parsing fails or the item is gone, the handler answers gracefully and does nothing
destructive (falls through to normal message routing).

## 8. Callback schema

New `item:*` namespace (all well under Telegram's 64-byte `callback_data` limit), parsed in
`app/commands.py` alongside the existing verbs:

| callback_data | meaning |
|---|---|
| `item:open:<id>` | open the item card |
| `item:list` | back to the list view (re-render digest) |
| `item:corr:<id>` | open the correct sub-menu |
| `item:nudge:<id>:<p7\|p3\|m3\|today>` | apply a shelf-life nudge, re-render the menu |
| `item:ctext:<id>` | start free-text correct (send ForceReply prompt) |
| `item:rm:<id>` | show the remove-confirm |
| `item:rmok:<id>` | confirm remove → `mark_removed`, re-render list |

Reused verbs (with one behavior change): `act:ate:<id>` / `act:toss:<id>` /
`act:snooze2:<id>` / `act:freeze:<id>` keep their handler logic but are now emitted by the
**card** keyboard, not the digest row; the handler continues to call
`_refresh_digest_message` afterward, which now renders the new labeled-button list.

**`show:all` changes behavior.** Today its handler sends a *separate, read-only*
`render_list` message (no buttons). In the drill-down model that defeats the purpose — the
whole reason to "show all" is to reach and act on items beyond the cap. The handler is
re-pointed to **re-render the same list-view message** (text + item-buttons) for *all* due
items, in place, so every shown item remains tappable.

## 9. Rendering changes (`app/renderer.py`, `app/i18n.py`)

`renderer.py` (pure / synchronous — unit-testable with exact-string assertions):

- `build_digest_keyboard(item_ids, *, has_more, lang)` → re-implemented to emit
  `item:open:<id>` labeled buttons (icon + `#id` + name, 2/row) + the `Show all` button.
  It needs the item objects (not just ids) to render labels — signature widens to take the
  rendered items (or `(id, icon, name)` tuples) so it stays pure.
- New `render_item_card(item, *, today, lang, names)` → the card text.
- New `build_item_card_keyboard(item, *, lang)` → the card keyboard (omits Freeze when
  frozen).
- New `build_correct_menu_keyboard(item_id, *, lang)` and a small `render_correct_menu(item,
  *, today, lang)` header.
- New `build_remove_confirm_keyboard(item_id, *, lang)` and `render_remove_confirm(item, *,
  lang)`.

`i18n.py`: new catalog keys for every new label/prompt
(`btn.back_to_list`, `btn.correct`, `btn.remove`, `btn.remove_yes`, `btn.cancel` (reuse if
present), `btn.nudge_plus_week`, `btn.nudge_plus_3d`, `btn.nudge_minus_3d`,
`btn.nudge_use_today`, `btn.correct_something_else`, `correct.menu_header`,
`remove.confirm`, `correct.freetext_prompt`, …) across `en|zh|fr|es`. English values must be
byte-identical-safe; the `tests/test_i18n.py` placeholder-parity integrity test must pass.

## 10. Edge handling

| Case | Handling |
|---|---|
| Item acted on by a teammate before you tap (multi-user household) | Re-fetch on open/action; `NotOwnerOrMissing` → "item not found", terminal status → "already updated"; then re-render the list. Reuses existing guards. |
| Tap Freeze on an already-frozen item | Freeze button is hidden on frozen cards; if reached via a stale message, `freeze_item` is idempotent (`was_already=True`). |
| Search unavailable during a Freeze tap | `freeze_item` already falls back to the conservative frozen default (v4.6 §7); tap still succeeds. |
| `Show all` then Back from a card | Returns to the **capped** list view (expansion not remembered in v1 — accepted minor). |
| Free-text Correct reply can't be parsed / item gone | Handler answers gracefully, no mutation, falls through to normal routing. |
| Nudge would push `days` out of `[1,730]` | Clamped (see §6). |
| Empty digest after the last action | Existing `digest.pantry_clear` message (unchanged). |
| Stale edit (message too old / deleted) | `edit_text` wrapped in the existing try/except logging pattern (`_safe_edit_cb` / `_refresh_digest_message`). |

## 11. Testing

Following the project's deterministic patterns (injected `today`, fake LLM/search clients,
no `datetime.now()` in services):

- **Renderer (pure):** `build_digest_keyboard` emits one `item:open:<id>` per capped item
  with correct `icon + #id + name` labels and 2/row layout; `Show all` appears iff
  `has_more`. `build_item_card_keyboard` omits Freeze for frozen items and includes it
  otherwise. Card / correct-menu / remove-confirm renderers produce exact expected strings.
- **Callback routing:** `item:open` → card; `item:list` → list; `item:corr` → menu;
  `item:rm` → confirm; `item:rmok` → `mark_removed` + list refresh; `act:*` from the card →
  the right service + list refresh.
- **Nudges:** each code computes the right `days` and calls `correct_item`; clamping at both
  bounds; `use by today` floor behavior; cache-learning side effect asserted.
- **Free-text Correct:** ForceReply prompt embeds a parseable id; the reply handler extracts
  it and invokes `propose_correct`; unparseable / missing-item replies are safe no-ops; the
  typed `/correct` command path is unaffected.
- **Remove confirm:** Yes removes; Cancel returns to the card; no single-tap removal path
  exists.
- **Concurrency:** acting on an already-terminal item answers "already updated" and
  re-renders the list (multi-user safety).
- **i18n:** catalog completeness + placeholder parity for all new keys; existing English
  digest strings unchanged.

## 12. Scope boundaries (YAGNI — not in v4.8)

- **`/list` stays read-only** — no drill-down cards there; the "freeze-early" gap (freezing
  a fresh item not yet near expiry) is deferred.
- No multi-duration snooze (card keeps `+2d`).
- No undo for terminal actions (Ate / Tossed / Remove remain non-undoable from the UI, as
  today).
- No true Prev/Next pagination (cap + `Show all` only).
- No remembering of the expanded ("Show all") state across a drill-down round-trip.
- No batch / multi-select action mode.
- No change to any action's domain semantics — purely how they're reached.

## 13. Rollout

Zero schema change, zero migration. The morning scheduled digest and the interactive
refresh share `render_digest` + `build_digest_keyboard`, so both pick up the new model in
one change. The only user-visible behavioral shift is the digest keyboard going from
per-item action rows to labeled item-buttons; all existing commands (`/list`, `/correct`,
`/remove`, `/snooze`, `/ate`, …) keep working unchanged.
