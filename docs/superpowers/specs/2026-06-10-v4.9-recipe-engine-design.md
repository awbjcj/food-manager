## 1. Goal

Make `/cook` return **real, linked, nutrition-backed** recipes instead of LLM-improvised
ones; let the user steer by **genre and purpose**, not just meal type + a handful of
cuisines; and let them pull **more or different** recipes when the first set misses,
without restarting `/cook`.

Three asks, one engine:

- **C — real recipes + real nutrition:** a structured recipe/nutrition API replaces
  LLM-generated recipes and LLM-guessed health scores.
- **B — genres + purpose:** a fuller cuisine list plus a new _purpose_ axis.
- **A — more when unsatisfied:** a regenerate loop (`More` / `Adjust`) over real results.

## 2. The core reframe (why the API changes the shape, not just the source)

Today `run_cook` runs three LLM stages — **selection** (pantry → item subset), **recipe**
(web search → exactly 3 recipes), **nutrition** (invent a 0–100 health score) — then
`blended_score` ranks them. The recipe and nutrition stages are precisely where LLM-only is
weakest: plausible-but-fake recipes/links and numbers with nothing behind them.

The reframe: **Spoonacular's `complexSearch` already encodes, as declarative parameters,
almost everything those stages reason about** — cuisine, diet, intolerances, meal `type`,
`maxReadyTime`, `includeIngredients`, `sort`, and it returns real `sourceUrl`, real
`nutrition`, `healthScore`, `spoonacularScore`, and `readyInMinutes`. So the recipe and
nutrition LLMs are not _improved_ — they are **replaced by a real source** and demoted to a
fallback. The **selection LLM stays** (the pantry-understanding brain that picks a coherent,
profile-respecting subset of expiring items); the API _supplies_ recipes for that subset.

This is the hybrid: **LLM selects, API supplies, real numbers rank.**

## 4. Architecture

A new **deep seam** isolates "where recipes come from" from "how `/cook` orchestrates":

```
app/recipe_source.py   (new)
  RecipeCriteria          # pure dataclass: the search intent
  SourcedRecipe           # a real recipe + its nutrition (provider-agnostic)
  RecipeSource (Protocol) # available() + async search(criteria) -> recipes (+ accrued cost)
    SpoonacularSource      # complexSearch adapter
    TheMealDbSource        # free real-link fallback adapter
    LlmRecipeSource        # wraps existing recipe+nutrition LLM clients
    ChainedRecipeSource    # tries adapters in order until "enough" results
```

**Deletion test:** delete `recipe_source.py` and the provider differences (Spoonacular's
points/param quirks, TheMealDB's missing nutrition, the LLM's two-call dance) reappear
smeared across `cook_service`. It concentrates that complexity behind one small interface —
a deep module. The interface (`criteria → real scored recipes`) is the test surface.

`cook_service.run_cook` changes from "call three LLMs" to:

1. `selection_llm.select_items(...)` — unchanged, but the prompt also carries `purpose`.
2. Build a `RecipeCriteria` from (selected items, profile, meal_type, cuisine, purpose,
   offset). **Pure function** `build_criteria(...)` — fully unit-testable.
3. `await source.search(criteria)` — the chain returns the recipes (and accrued API/LLM
   cost, which `run_cook` records on the `CookSession` exactly as today).
4. Post-filter with the existing `violates_exclusions` (defense beyond API `intolerances`),
   rank with `blended_score`, attach `shopping_list` for the top card. Unchanged math.

Files touched: **new** `app/recipe_source.py` (including `LlmRecipeSource`, which wraps
the existing recipe+nutrition clients); `app/cook_models.py` (add `RecipeCriteria`,
`SourcedRecipe`, `Purpose`); `app/cook_service.py` (orchestration); `app/settings.py`
(Spoonacular key); `app/bot.py` (purpose round, cuisine-more, `More`/`Adjust` callbacks);
`app/i18n.py` (new chrome); one Alembic migration (`CookSession` columns). `app/cook_llm.py`
keeps the existing LLM clients unchanged.

## 5. The `RecipeSource` interface

```python
class Purpose(str, Enum):
    USE_IT_UP = "use_it_up"
    QUICK = "quick"
    HEALTHY = "healthy"
    COMFORT = "comfort"
    SURPRISE = "surprise"


@dataclass(frozen=True)
class RecipeCriteria:
    include_ingredients: list[str]      # normalized names of the selected pantry items
    meal_type: Optional[str]            # Spoonacular `type`
    cuisine: Optional[str]              # None / "surprise" => no cuisine filter
    purpose: Purpose
    diet: Optional[str]                 # from profile.diet
    intolerances: list[str]             # from profile.exclusions (mapped)
    exclude_ingredients: list[str]      # from profile.exclusions
    max_ready_minutes: Optional[int]    # purpose=quick or profile.max_cook_minutes
    number: int                         # page size (default 6: one top card + alternatives)
    offset: int                         # pagination cursor (advanced by `More`)


class SourcedRecipe(BaseModel):
    recipe: RecipeCandidate             # existing model (title, cuisine, source_url, ingredients, method_gist, deliciousness)
    nutrition: NutritionScore           # existing model (health_score, effort, est_minutes, rationale)
    external_id: Optional[str] = None   # provider recipe id, for dedup across pages


class RecipeSource(Protocol):
    def available(self) -> bool: ...
    async def search(self, criteria: RecipeCriteria) -> tuple[list[SourcedRecipe], Optional[int]]: ...
    #                                                    recipes, cost_micros (None if free/unknown)
```

`ChainedRecipeSource.search` calls each adapter in order; the first to return at least one
recipe wins. Empty/unavailable adapters (missing key, quota error, network failure) are
swallowed and the chain advances — mirroring the cook LLM retry/again philosophy and the
frozen resolver's graceful fallback. Profile-safety filtering stays in `cook_service`, where
the pantry/profile ranking context already lives; adapters still pass API-level exclusion
params when the provider supports them.

## 6. SpoonacularSource — the primary adapter

One `GET /recipes/complexSearch` call with:

| `RecipeCriteria` field | query param                                                                                                             |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `include_ingredients`  | `includeIngredients` (comma-joined)                                                                                     |
| `meal_type`            | `type` (mapped: Dinner/Lunch→`main course`, Breakfast→`breakfast`, Dessert→`dessert`, Snack→`snack`, Surprise→omit)     |
| `cuisine`              | `cuisine` (omit for surprise)                                                                                           |
| `diet`                 | `diet`                                                                                                                  |
| `intolerances`         | `intolerances` (comma-joined)                                                                                           |
| `exclude_ingredients`  | `excludeIngredients` (comma-joined)                                                                                     |
| `max_ready_minutes`    | `maxReadyTime`                                                                                                          |
| `number` / `offset`    | `number` / `offset`                                                                                                     |
| purpose sort           | `sort` = `max-used-ingredients` (use-it-up) / `healthiness` (healthy) / `popularity` (comfort); omit for quick/surprise |

Always sent: `addRecipeInformation=true`, `addRecipeNutrition=true`, `fillIngredients=true`,
`apiKey=<SPOONACULAR_API_KEY>`. Mapping the JSON response to `SourcedRecipe`:

- `recipe.title` ← `title`; `recipe.source_url` ← `sourceUrl`; `recipe.cuisine` ← first of
  `cuisines` (or the requested cuisine); `recipe.ingredients` ← `extendedIngredients`
  (name/amount/unit); `recipe.method_gist` ← a trimmed join of `analyzedInstructions` steps;
  `recipe.deliciousness` ← `spoonacularScore/100` (clamped 0–1).
- `nutrition.health_score` ← `healthScore` (0–100); `nutrition.est_minutes` ←
  `readyInMinutes`; `nutrition.effort` ← bucket(`readyInMinutes`: ≤20 easy, ≤45 medium, else
  hard); `nutrition.rationale` ← a short real-nutrition summary (calories + macros from
  `nutrition.nutrients`).
- `external_id` ← `id`.

> **Licensing:** Spoonacular requires attribution/linking; the card already shows
> `source_url`. We store only ids + the snapshot needed for Save/re-cook (as today), which is
> within terms; no bulk catalog storage.

## 7. TheMealDbSource — the free fallback adapter

When Spoonacular is unavailable (no key / quota / error), fall back to a free path:

- **TheMealDB** `filter.php` by main ingredient (the most-urgent selected item) and/or
  `a=<area>` for cuisine, then `lookup.php?i=<id>` for the full recipe (ingredients,
  instructions, source/YouTube link). No API key needed for the public dev endpoints.
- TheMealDB does **not** provide dependable nutrition. This adapter returns a neutral
  `NutritionScore(health_score=50, effort="medium", est_minutes=30)` with rationale
  `"nutrition unavailable"`. Honest degradation — still a **real** recipe with a **real**
  link, without adding a shallow nutrition-provider setting that no implementation uses.

This adapter is intentionally simpler than Spoonacular: it cannot honor every filter
(diet/intolerances are applied only via the post-`violates_exclusions` filter). It exists to
keep `/cook` producing real recipes when the primary quota is spent.

## 8. LlmRecipeSource — the last-resort adapter

Wraps the **existing** `RecipeLLMClient` + `NutritionLLMClient` (web-search recipe
generation and nutrition scoring) behind the `RecipeSource` interface, reusing today's
`run_cook` logic (including the exclusion-aware regenerate). It runs only when both real
sources fail or are unconfigured, guaranteeing `/cook` always answers. The existing
`COOK_COST_CEILING_MICROS` guard still applies on this path.

## 9. Intake — three one-tap rounds

`handle_cook` → rounds, each a `build_cook_round_keyboard` step (reusing the existing
`cookpick:<cook_id>:<round>:<idx>` mechanism):

1. **meal** — `MEAL_TYPES` (unchanged).
2. **cuisine** — `_cuisine_options` quick picks (household prefs first) **+ a
   `More cuisines »` button** (`cookmore:<cook_id>:cuisine_full`) that re-renders the round
   with the full Spoonacular cuisine list; `Any/Surprise me` always present. Full-list picks
   emit `cookpick:<cook_id>:cuisine_full:<idx>` so the index is stateless and never confused
   with the quick-pick list.
3. **purpose** — `Use it up / Quick / Healthy / Comfort / Surprise me`.

After the purpose pick, the session is `ready` and `run_cook` fires (today's "Thinking…" →
`run_cook_and_render` path, unchanged in shape).

## 10. Result card + regenerate

The card content is unchanged (title, cuisine, real health/effort/minutes, real ingredients,
real `source_url`, shopping diff). Two buttons are added to the existing keyboard:

- **`🔄 More`** (`cookmore2:<cook_id>`) — advance `search_offset` by `number`, re-run the
  source `search` with the **same** `RecipeCriteria`, drop any `external_id` already shown,
  prepend the new page to `candidates_json` while retaining old cards for future dedup, then
  re-render with the new top card. If the source returns nothing new → "no more recipes for
  these filters — try Adjust."
- **`🎛 Adjust`** (`cookadj:<cook_id>`) — return to the **cuisine** round (then purpose),
  keeping the existing `selected_item_ids`; on the next purpose pick, reset `search_offset=0`
  and re-search.

Existing buttons (`Liked`/`Disliked`/`Save`/`Add to shopping`/`Show alternatives`) are
unchanged.

## 11. State & schema — one Alembic migration

`CookSession` gains two additive columns:

| column          | type                            | notes                                                         |
| --------------- | ------------------------------- | ------------------------------------------------------------- |
| `purpose`       | `Optional[str]`, default `NULL` | the chosen `Purpose` value; `NULL` for legacy/in-flight rows. |
| `search_offset` | `int`, default `0`              | pagination cursor for `More`.                                 |

Shown-recipe dedup keys off `external_id` inside the existing `candidates_json` (no new
column). `selected_item_ids`, `meal_type`, `cuisine`, `candidates_json`, `chosen_index`
remain as today. Migration is purely additive; existing rows get `purpose=NULL`,
`search_offset=0`.

## 13. Edge handling

| Case                                                       | Handling                                                                                            |
| ---------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| No `SPOONACULAR_API_KEY`                                   | Spoonacular adapter unavailable; chain falls to TheMealDB, then LLM.                                |
| Spoonacular quota/HTTP error                               | Swallowed; chain advances. Logged with `error_class`.                                               |
| Spoonacular returns 0 for tight filters                    | Treated as "adapter yielded nothing"; chain advances (so a real recipe still appears via fallback). |
| `More` finds no new recipes                                | Friendly "no more — try Adjust"; card unchanged.                                                    |
| All sources fail                                           | "couldn't find recipes right now — try again" (same spirit as today's empty result).                |
| Profile exclusion not an API intolerance (e.g. "cilantro") | Caught by the retained `violates_exclusions` post-filter.                                           |
| TheMealDB fallback has no nutrition                        | Recipe shown with "nutrition unavailable"; ranking uses neutral defaults.                           |
| Legacy in-flight `CookSession` (pre-migration)             | `purpose=NULL` treated as `Surprise`; `search_offset=0`.                                            |

## 14. Testing

Deterministic, injected clients (no real HTTP in tests — a `FakeRecipeSource` and a fake
HTTP client mirroring `tests/fakes.py`):

- **`build_criteria` (pure):** purpose→sort/maxReadyTime mapping; meal_type→`type` mapping;
  profile diet/exclusions→`diet`/`intolerances`/`excludeIngredients`; offset/number.
- **SpoonacularSource:** maps a canned `complexSearch` JSON to `SourcedRecipe` (sourceUrl,
  real nutrition, deliciousness from spoonacularScore, effort buckets); builds correct query
  params; HTTP error → empty + cost None.
- **ChainedRecipeSource:** primary empty/unavailable → fallback used; all empty → LLM
  adapter used; first non-empty wins.
- **Ranking:** `blended_score` fed real numbers orders as expected; `violates_exclusions`
  drops an unsafe API recipe.
- **Regenerate:** `More` advances `search_offset`, dedups `external_id`, appends candidates;
  empty next page → friendly message. `Adjust` returns to cuisine round, keeps
  `selected_item_ids`, resets offset on re-search.
- **Intake:** purpose round options; `More cuisines »` expands to the full list; surprise
  omits filters.
- **Gate:** the existing cook-selector gate remains; an empty static-source list still
  works through the per-user LLM tail.
- **Migration:** `CookSession` round-trips `purpose`/`search_offset`; legacy row defaults.
- **i18n:** new chrome (purpose labels, More/Adjust, more-cuisines) across en/zh/fr/es;
  placeholder parity holds.

## 15. Scope boundaries (YAGNI — not in v4.9)

- **No v3.6 affinity / personalization** (separate track).
- No Edamam, no meal-planning, no recipe images, no cost/price display.
- No caching layer beyond reusing `candidates_json` within a cook session (one household's
  quota is ample; a cross-session recipe cache is deferred).
- No new `/cook` argument syntax — intake stays button-driven.
- TheMealDB fallback is best-effort and nutrition-neutral; not held to Spoonacular's
  fidelity.
- No change to the existing Save/re-cook (`favorites_service`) or shopping
  (`shopping_service`) behavior beyond consuming real `SourcedRecipe` fields.

## 16. Rollout

Additive migration (new `CookSession` columns, safe defaults). Without
`SPOONACULAR_API_KEY` the bot still has real-link fallback through TheMealDB and then the LLM
tail; adding the key flips the primary source to nutrition-backed Spoonacular recipes with
**no further change**. The intake gains one round (purpose) and a cuisine expansion; the
result card gains two buttons. No existing command syntax changes.
