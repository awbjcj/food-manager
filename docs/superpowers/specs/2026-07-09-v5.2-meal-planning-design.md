# Food Manager v5.2 — Meal Planning

**Status:** Design approved (pending spec review)
**Date:** 2026-07-09
**Lineage:** Track 5 of the v5 roadmap (`2026-07-08-v5-roadmap-design.md`).
**Prerequisites:** v4.9 tasks 9–14 shipped (`RecipeCriteria` + wired source chain +
`search_offset` pagination, per the plan as refreshed 2026-07-08) and v5.1 shipped
(the per-provider Agno agent bootstrap pattern).
**Staleness clause (deliberate):** this spec was written ahead of its prerequisites
at the user's request. Before its implementation plan is *executed*, it gets a
refresh checkpoint against the actual shipped v4.9/v5.1 code — the same pass that
caught the v4.9 drift on 2026-07-08.

## 1. Goal

`/plan` turns the pantry into a week of dinners: one recipe per day for a
user-chosen 3–7 days (default 5), scheduled so soon-to-expire items get cooked
first, with per-day swaps and one aggregated shopping list for everything the
pantry can't cover.

## 2. Locked decisions (via grilling)

| Decision | Choice | Why |
|---|---|---|
| Plan shape | **Dinners only, 3–7 days (default 5)** | Dinner is where /cook already lives and expiring items get used; 21 meals/week triples cost and produces plans nobody follows. Breakfast/lunch later, if ever. |
| Consumption model | **Greedy sequential allocation** | Day N plans against the pantry minus days 1..N-1's ingredients; expiring items are assigned to the earliest days. Pure function — the shopping list is correct by construction and the same spinach can't be recommended five nights running. |
| Persistence | **`MealPlan` + `MealPlanEntry` tables** | Swap buttons need stateless callbacks that reload the plan (v4.8 rule), the shopping aggregate needs final entries, and a future digest can say "tonight: X". One additive migration. |
| Agno's role | **One `WeekComposer` agent, plain-Python orchestrator** | The only LLM-shaped step is composing a varied week; gather/allocate/fetch/aggregate are deterministic and need tight session control. This satisfies the roadmap's Agno boundary without Workflow ceremony (deliberate deviation from the roadmap's literal "Agno Workflow" wording, approved 2026-07-09). |

## 3. Data model

One additive migration:

- **`MealPlan`**: `id`, `household_id` (indexed), `start_date`, `days` (3–7),
  `status` (`draft | active | cancelled`), `cost_micros_usd`, `chat_id`,
  `message_id`, `created_at`. One *active* plan per household — a new `/plan`
  marks the previous one `cancelled`.
- **`MealPlanEntry`**: `id`, `plan_id` (indexed), `day_index` (0-based),
  `date`, `recipe_json` (the same `ScoredCandidate` payload shape `/cook`
  persists in `candidates_json`, including `external_id`), `shopping_json`
  (that day's ingredient gap vs the allocated pantry pool).

All state a button needs is re-derived from `plan:<verb>:<plan_id>[:<day>]`
callback data plus these rows — stateless, restart-safe.

## 4. Planning pipeline (`app/plan_service.py`)

`build_plan(session, *, household_id, user, days, composer, source, today, …)`:

1. **Gather.** Active pantry items with expiry dates; `FoodProfile` from the
   household.
2. **Compose — the Agno seam.** A `WeekComposer` agent (structured output) maps
   `(pantry names + days-to-expiry, profile, day count)` to a list of `DaySpec`s:
   `cuisine`, `purpose` (v4.9 `Purpose`), and `feature_items` (which expiring
   pantry items that day should use). Variety is its job: no five pasta nights,
   preferred cuisines rotated, expiring items spread sensibly. Built per provider
   at bootstrap and selected by `User.llm_provider` — the exact v5.1
   `IntentAgentSelector` pattern (classify/compose only; never touches DB or
   Telegram; faked in tests).
   **Fallback:** any composer failure logs and falls back to a pure heuristic
   (rotate the profile's preferred cuisines, assign items greedily by earliest
   expiry) so `/plan` always answers — the same guarantee shape as the v4.9 LLM
   tail.
3. **Fetch with sequential allocation.** For each day in order: build a v4.9
   `RecipeCriteria` from the `DaySpec` and the *remaining* pantry pool
   (`include_ingredients` = that day's allocated/feature items), search the
   chained `RecipeSource`, take the top `blended_score` candidate not already in
   the plan (dedup by `external_id`), subtract its pantry-matched ingredients
   from the pool, and record the day's shopping diff (via the existing
   `shopping_list` gap logic). An empty search result for a day falls back to
   relaxing cuisine (None) before giving up on that day.
4. **Persist + render.** Write `MealPlan` + entries (`status="active"`), render
   one message — a line per day (localized weekday, title, cuisine, est. minutes,
   🔥 marker when the day uses expiring items) — with buttons: `🔄 Swap` per day
   (`plan:swap:<id>:<day>`), `➕ Shopping list` (`plan:shop:<id>`), `❌ Cancel`
   (`plan:cancel:<id>`).

Costs from composer + source searches accrue onto `MealPlan.cost_micros_usd`;
a `PLAN_COST_CEILING_MICROS` setting bails out with partial results, mirroring
`COOK_COST_CEILING_MICROS`.

`/plan` is a slow command: it uses the v5.0 progress ack
(`start_progress`/`finish_progress`) like photo ingest.

## 5. Interactions

- **Swap day N** (`plan:swap`): re-search that day's stored criteria with an
  advanced `offset` (v4.9 pagination), dedup by `external_id` against every
  recipe in the plan, replace the entry (and its shopping diff), re-render in
  place via `callback_dispatch`. Other days are not re-composed. No further
  results → answer with the v4.9 `cook.no_more`-style copy.
- **Shopping list** (`plan:shop`): union of per-day `shopping_json` diffs,
  deduped by `normalized_name` against both the pantry and the household's
  existing shopping list, inserted through `shopping_service`; the message is
  edited to confirm what was added. Idempotent: a second tap adds nothing new.
- **Cancel** (`plan:cancel`): plan `status="cancelled"`, message edited to a
  short confirmation.
- **Supersede**: `/plan` while a plan is active cancels the old one (noted in
  the new plan's reply).

**Deferred, enabled by this model but not built in v5.2:** "tonight: X" line in
the morning digest; marking a day cooked (and pantry decrement on cook); NL
"plan my week" intent (one line in the v5.1 agent's schema when its turn comes).

## 6. i18n

New catalog keys (en/zh/fr/es, placeholder parity enforced): plan header/day
line/expiring marker legend, button labels (swap/shopping/cancel), progress ack
("🗓 Planning your week…"), empty-pantry reply, no-more-swaps, shopping-added
confirmation, plan-cancelled, plan-superseded note. Weekdays reuse the existing
locale helpers in `app/i18n.py`.

## 7. Testing

House patterns: injected `session`/`today`, fakes over network.

- **Allocation (pure):** expiring items land in the earliest days; the pool
  depletes as days consume it; dedup by `external_id`; shopping union is exactly
  (recipes − pantry) with no double-count across days.
- **Composer seam:** `FakeWeekComposer` returns canned `DaySpec`s; composer
  raising → heuristic fallback produces a full plan.
- **Source integration:** `FakeRecipeSource` canned per criteria; empty-result
  relaxation path.
- **Callbacks:** swap replaces exactly one entry and re-renders; shop is
  idempotent; cancel terminal; all reload state from DB (simulated restart).
- **Cost ceiling:** pipeline stops and returns partial plan past the ceiling.
- **Migration:** alembic upgrade on the migration suite; one-active-plan
  supersede behavior.
- **i18n:** key completeness + placeholder parity; English renderer output
  exact-string tested.

## 8. Scope boundaries (YAGNI — not in v5.2)

- No breakfast/lunch planning, no multi-week plans.
- No digest integration or cooked-tracking (deferred, see §5).
- No re-compose-the-whole-week button (swap is per-day only).
- No portion/quantity math beyond ingredient-name matching (quantities stay
  out of the allocation model, as in /cook's shopping diff today).
- No calendar export.
