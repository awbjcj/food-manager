# Food Manager v5.3 — Affinity Learning + Recipe Media

**Status:** Design approved (pending spec review)
**Date:** 2026-07-09
**Lineage:** Track 6 of the v5 roadmap (`2026-07-08-v5-roadmap-design.md`). Revives
the v3.6 learning-loop design locked in `2026-05-30-cook-v3.5-design.md` §7,
updated here for the v4.9 multi-source world.
**Prerequisites:** v4.9 tasks 9–14 shipped (source mappers to extend, LLM tail to
steer). v5.2 is *optional*: `/plan` inherits affinity automatically through the
shared `blended_score` if it exists; nothing here branches on it.
**Staleness clause:** written ahead of prerequisites at the user's request; the
implementation plan gets a refresh checkpoint against shipped code before
execution (same procedure as v5.2's Task 0).

## 1. Goal

Two upgrades to recipe results. **Affinity:** the 👍/👎 feedback `/cook` has been
recording since v3.5 finally changes what gets recommended — dishes similar to
liked ones rank higher, similar to disliked ones lower, across every recipe
source. **Media:** real-source recipes show their photo (via link preview) and an
"Open recipe" button.

## 2. Locked decisions (via grilling, updating v3.6 §7)

| Decision | Choice | Why |
|---|---|---|
| Mechanism | **Hybrid, as locked in v3.6**: deterministic affinity term in `blended_score` + capped steering summary in LLM prompts | The term is testable and re-ranks candidates from *any* source (the v4.9 update: Spoonacular/TheMealDB results get taste-ranked too); the summary steers only what can be steered — LLM generation. |
| Weights | `0.3·health + 0.3·expiry + 0.2·deliciousness + 0.2·affinity` | 0.2 breaks ties without letting taste override expiring food (the app's core job). |
| Dislikes | **Always soft** — never promoted to hard `exclusions[]` | A disliked dish is a preference; exclusions are safety/diet. Unchanged from v3.6. |
| Scope | **Everywhere `blended_score` runs** — `/cook` now, `/plan` automatically when v5.2 ships | One shared function; zero conditional code. |
| Signal window | **Most recent 50 signals per household, unweighted** | Deterministic, testable, self-correcting as tastes change; no decay-curve tuning that can't be validated at household scale. |
| Cold start | **No signals → affinity is a constant 0.5** | Ranking provably unchanged until feedback exists; the constant keeps score magnitudes centered. |
| Media | **Link preview + URL button; text cards unchanged** | Telegram can't edit a text message into a photo message, and /cook//plan cards are edited in place; the source-URL preview carries the recipe photo with zero message-model churn. |

## 3. Affinity term (`app/cook/affinity.py`, new)

- `list_recent_signals(session, *, household_id: int, limit: int = 50) ->
  list[FeedbackSignal]` — the household's most recent liked/disliked sessions by
  `feedback_at`, reconstructed via the existing, test-locked
  `cook.feedback.feedback_signal()` contract (`cuisine`, `ingredients`,
  `verdict`).
- `affinity(*, cuisine: str, ingredient_names: list[str],
  signals: Sequence[FeedbackSignal]) -> float` — pure, in `[0, 1]`, `0.5` when
  `signals` is empty. Computation: for each signal, a similarity in `[0, 1]` =
  ½·(cuisine exact-match after `normalize`) + ½·(normalized ingredient-set
  overlap, Jaccard); liked similarities count positive, disliked negative;
  the mean is mapped from `[-1, 1]` to `[0, 1]`. Exact constants live in the
  implementation plan; the invariants that matter (and are test-pinned):
  liked-similar > neutral > disliked-similar; a dish similar only to dislikes
  still gets a nonzero score (soft); empty signals → exactly `0.5`.
- `blended_score(*, health_0_1, expiry_use, deliciousness, affinity_0_1)` gains
  the fourth argument and the new weights. Every existing test pinning
  three-term outputs is updated in the same task — a deliberate, reviewed
  break, not drift.
- Call sites (`run_cook`'s scoring loop; v5.2 `plan_service._score` if present)
  fetch signals once per pipeline run and pass the computed term in.

## 4. Steering summary (LLM tail + composer only)

- `steering_summary(signals, *, max_chars: int = 200) -> str` — deterministic:
  top 3 liked cuisines, top 3 liked ingredients, top 3 disliked of each, ties
  broken alphabetically, truncated at a word boundary under `max_chars`.
  Example: `Household taste: likes thai, mexican; loves tofu, lime. Dislikes:
  cream-heavy dishes, celery.`
- Injected into the v4.9 LLM-tail recipe prompt and (when present) the v5.2
  `WeekComposer` prompt. Real-source API queries are **not** modified — they're
  covered by the re-ranking term.
- **Empty signals → no injection at all**: the prompts stay byte-identical to
  today, keeping cold-start behavior pinned by existing prompt tests.

## 5. Recipe media

- `RecipeCandidate.image_url: Optional[str] = None` — pydantic payload only
  (persists inside `candidates_json` / `recipe_json`); **no DB migration**.
- Mappers: Spoonacular's `image` field and TheMealDB's `strMealThumb` populate
  it; the LLM tail leaves it `None`. (`source_url` already exists on
  `RecipeCandidate`.)
- Rendering: result cards stay text and edit-in-place. When `source_url` is
  present: enable Telegram's link preview on the card (the preview renders the
  recipe photo — `image_url` is carried for future use and preview fallback)
  and append an `🔗 Open recipe` **URL button** (URL buttons need no callback
  handling). Recipes without a `source_url` render exactly as today, byte-for-
  byte. One new i18n key: `btn.open_recipe` (en/zh/fr/es).

## 6. Testing

- **Affinity (pure):** liked-similar dish outranks neutral outranks
  disliked-similar; dislike suppresses but never zeroes (soft); empty signals →
  exactly 0.5 and unchanged ranking vs the old blend; window truncates at 50
  most recent; determinism (same inputs → same float).
- **Steering:** deterministic output for a fixed signal set; ≤ max_chars;
  empty signals → empty string and byte-identical prompts.
- **Blend regression:** every test pinning `blended_score` updated; a dedicated
  test locks the new weights summing to 1.0.
- **Mappers:** `image_url` extracted from canned Spoonacular/TheMealDB payloads
  (extend `tests/test_recipe_source.py`).
- **Renderer:** exact-string card with and without `source_url`; URL button
  present only when a URL exists; i18n parity for the new key.

## 7. Scope boundaries (YAGNI — not in v5.3)

- No per-user affinity (the signal and the term are household-level, like the
  pantry and profile).
- No decay/recency weighting beyond the recent-50 window.
- No feedback UI changes (👍/👎 stays as shipped in v3.5).
- No photo-message cards (revisit only if link previews prove insufficient).
- No affinity influence on shopping list, favorites, or ingest.
- Deferred from v3.5 and still deferred: dish dedup/history view.
