# Food Manager v5.4 — Waste & Consumption Analytics

**Status:** Design approved (pending spec review)
**Date:** 2026-07-09
**Lineage:** Track 7 (final) of the v5 roadmap (`2026-07-08-v5-roadmap-design.md`).
**Prerequisites:** none — this touches only `PantryItem` terminal mutations and a
new read-only report path, none of which v4.9/v5.0–v5.3 change. It sits last in
the roadmap by priority, not by dependency, and needs no staleness clause.

## 1. Goal

Answer "how are we actually doing?": what gets eaten vs tossed, which foods keep
getting wasted, and whether it's improving — via an on-demand `/stats` report.

## 2. Locked decisions (via grilling)

| Decision | Choice | Why |
|---|---|---|
| History mechanism | **`PantryItem.resolved_on: Optional[date]`** — one column, one additive migration | Terminal rows are never deleted, so the only missing fact is *when* they resolved. One column answers every v5.4 question. A `PantryEvent` log (freezes/snoozes/corrections) records events nothing consumes and can't be backfilled either — rejected as speculative. |
| Backfill | **None — existing terminal rows stay `NULL`** | All-time counts work immediately; time-bucketed stats accrue from ship. The report says so honestly when `NULL`s fall in range. |
| `removed` status | **Excluded from waste analytics** | "Removed" means "shouldn't have been tracked" (a mis-scan), not a consumption outcome. Waste rate = tossed / (eaten + tossed). |
| Surface | **`/stats week\|month\|all`; bare `/stats` keeps the shipped ops report** | On-demand pure-query report. No scheduled push (noise), no digest clutter. *(Amended at plan time 2026-07-09: the spec originally said "default month", not knowing `/stats` already ships a 30-day ops/cost report that ignores arguments. User chose split-by-argument: bare `/stats` stays byte-identical; a window token selects the new waste report.)* |
| Intelligence | **Deterministic only — no LLM** | Counts, rates, and one rule-table nudge line. Nothing here benefits from a model call. |

## 3. Data change

- `PantryItem.resolved_on: Optional[date] = None`, set to the caller-provided
  `today` inside `pantry_service._set_terminal` (covers `mark_eaten` /
  `mark_tossed`) and `mark_removed`. The `today` parameter already flows in —
  zero new clock plumbing.
- One additive migration (next free number at implementation time), nullable,
  no server default, no backfill.

## 4. Report (`app/stats_service.py` + renderer)

`waste_stats(session, *, household_id: int, since: Optional[date], today: date)
-> WasteStats` — a pure-query dataclass:

- eaten count, tossed count, waste rate (tossed / (eaten + tossed); rate line
  omitted when both are zero);
- top 3 tossed foods by `normalized_name` (count each);
- per-category eaten/tossed counts;
- tossed split: already-expired at resolution (`resolved_on > expires_on`) vs
  tossed early — `expires_on` is on every row, so this is free;
- the same aggregates for the previous equal-length window, for a delta line
  (`all` has no delta);
- a `window_truncated` flag when terminal rows with `NULL resolved_on` exist for
  the household (the renderer adds one honest footnote line).

`/stats week|month|all` — `parse_stats_arg` in `app/commands.py` (no args →
`None`, meaning the existing ops report renders unchanged; any other token →
usage error). Handler follows house style: `_request`
auth, service call, two-phase render (food names translated via
`translate_texts`), pure sync renderer, new i18n keys across en/zh/fr/es with
placeholder parity.

**Nudge line (deterministic).** The report ends with at most one callout picked
from a fixed rule table evaluated against the window's stats, first match wins:

1. Most-tossed food was mostly tossed *expired* → suggest freezing it sooner
   (`❄️`, ties into v4.6 storage states).
2. Most-tossed food was mostly tossed *early* → suggest buying less of it.
3. Waste rate improved vs previous period → a one-line cheer.
4. Otherwise → no callout.

## 5. Testing

- **Service:** window boundary math (week = 7 days, month = 30 days back from
  `today`; previous window adjacent and equal); `NULL resolved_on` rows excluded
  from windowed stats but counted all-time; `removed` excluded everywhere;
  expired-vs-early split; top-tossed ordering and tie behavior; delta
  computation; `window_truncated` flag.
- **Nudge rules:** each rule's trigger + first-match-wins precedence + the
  no-callout case.
- **Renderer:** exact English strings for a populated report, an empty report,
  and the truncation footnote; i18n key parity.
- **Mutations:** `mark_eaten`/`mark_tossed`/`mark_removed` set `resolved_on =
  today` (extend the existing pantry-service tests).
- **Migration:** covered by the migration suite.

## 6. Scope boundaries (YAGNI — not in v5.4)

- No money/price stats — receipts don't capture per-item prices; noted as a
  possible future receipt-parse extension, not designed here.
- No charts or images; text report only.
- No scheduled/push delivery; on-demand command only.
- No `PantryEvent` log; no tracking of freezes/snoozes/corrections.
- No per-user attribution (household-level, like everything else).
- No custom date ranges beyond the three windows.
