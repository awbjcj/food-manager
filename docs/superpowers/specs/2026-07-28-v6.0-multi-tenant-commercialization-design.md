# Food Manager v6.0 — Multi-Tenant Commercialization (Registration, Billing, Quota)

**Status:** Design approved, ready for implementation planning
**Date:** 2026-07-28
**Author:** awbjcj (with Claude)
**Builds on:** v4.0 tenancy overhaul (`2026-05-31-v4-tenancy-overhaul-design.md`) and the v5.x feature set shipped through v5.3
**Followed by:** implementation plan `docs/superpowers/plans/2026-07-28-v6.0-multi-tenant-commercialization.md`

---

## 1. Summary

The bot is technically multi-tenant but commercially single-tenant. Every domain row is
already keyed by `household_id` (v4.0), yet access is gated by a single
`ALLOWED_TELEGRAM_USER_ID` env var, there is no notion of entitlement, and nothing bounds
what a household can spend of the operator's LLM budget.

v6.0 turns the bot into a **public product**: anyone can register, households run on a
metered free tier, and a paid tier is bought in-bot with **Telegram Stars**. A separate
**operator bot** gives the operator grant/refund/ban controls. Quota is **pooled per
household**, enforced at the handler boundary, and backed by a real-cost circuit breaker
derived from the `cost_micros_usd` metering that already flows through every provider call.

This is an **entitlement layer**, not a re-architecture. It adds one orthogonal axis
(may this household spend?) on top of an existing one (who owns this row?). No existing
domain table changes shape.

---

## 2. Goals

- **Open registration.** Any Telegram user can `/start` and get a working free-tier
  household. No redeploy, no manual allowlist.
- **Bounded cost per household.** No household can consume unbounded LLM spend, whichever
  provider they select.
- **In-bot payment.** Subscribe and top up without leaving Telegram, via Stars.
- **Legible quota.** A member can ask `/quota` and get two numbers they understand plus a
  breakdown, in their own language.
- **Seat caps.** Free households hold 2 members, paid households up to 10.
- **Operator control.** Grant, refund, ban, and reconcile against Telegram's own ledger.
- **The bot stays useful at zero quota.** Exhaustion degrades to the non-LLM paths already
  in the codebase rather than bricking the bot.

## 3. Non-goals (explicit; deferred)

- **Multiple paid tiers.** One paid tier (`family`). The `PlanTier` literal and the
  `plans.py` catalog are shaped so a second tier is data, not code — but v6.0 ships one.
- **Proration, upgrades mid-period, annual billing.** Stars subscriptions are a fixed
  30-day period; v6.0 does not model partial periods.
- **Per-member quota attribution.** Quota is pooled at the household. We do not track
  which member spent it. (Same reasoning v4.0 used to reject per-row actor attribution.)
- **Non-Stars payment rails.** The `PaymentProvider` Protocol exists so a second rail is
  additive, but only `StarsPaymentProvider` is implemented.
- **Postgres migration.** See §11. Deliberately deferred.
- **Anti-abuse beyond `/ban`.** No phone verification, no device fingerprinting. See §13.
- **A web dashboard.** Everything is in Telegram.

## 4. Decisions locked (from the design conversation)

| # | Decision | Rationale |
|---|---|---|
| 1 | Public product, open registration | Determines rail, fraud posture, and free-tier need |
| 2 | Telegram Stars now, behind a `PaymentProvider` Protocol | Keeps the polling-only deployment; digital goods policy; mirrors the existing `LLMClient`/`ProviderSelector` seam style |
| 3 | Hybrid quota: receipts counter + weighted action pool + hidden cost breaker | Two legible numbers; the breaker makes provider-cost variance survivable |
| 4 | One customer bot + a separate operator bot, both in one process | Customer funnel stays one deep link; operator surface is invisible to customers; SQLite forces one process |
| 5 | Quota pooled per household; seat cap is a plan attribute | Matches `household_id` ownership; seats become an upgrade lever |
| 6 | Top-up packs that expire at period end | Works with the Stars rail rather than against it; bounds liability to one period |
| 7 | Small permanent free tier | Cold discovery converts at ~0 without one |
| 8 | Receipts hard-block; other ops degrade | No non-vision fallback exists for receipts; everything else has one already |

## 5. Architecture

### 5.1 New modules

```
app/billing/
  __init__.py
  plans.py         # PlanTier catalog: quotas, seat caps, SKUs, prices, weights.
                   # Pure data + pure functions. No I/O, no session.
  meter.py         # OpClass, weights, provider multipliers, admit() / commit().
                   # THE enforcement seam.
  entitlement.py   # Subscription state machine, lazy period rollover,
                   # apply_payment() / apply_refund() / apply_grant().
  payment.py       # PaymentProvider Protocol + StarsPaymentProvider.
  ledger.py        # PaymentEvent append-only writes; idempotency by charge id.

app/handlers/billing.py   # /quota, /buy, /billing + pre_checkout + successful_payment
app/operator/
  __init__.py
  bot.py           # second Dispatcher: /whois /grant /refund /ban /unban /revenue /reconcile
  auth.py          # operator identity check
```

`app/billing/` is a package for the same reason `app/cook/` is: it is a cohesive
subsystem with more than three modules. New SQLModel tables go in `app/models.py`,
following the existing one-models-file convention.

### 5.2 Conventions inherited (non-negotiable)

Every new service function follows the house rules stated in `CLAUDE.md`:

- **Session injection**: `session: Session` is the first argument. No global state.
- **Explicit `now: datetime` / `today: date`**: no internal clock reads, so tests are
  deterministic without mocking.
- **Protocol + fake**: `PaymentProvider` is a `Protocol`; `FakePaymentProvider` in
  `tests/fakes.py` satisfies it by duck typing, exactly as `FakeLLMClient` does.
- **Two-phase render**: quota cards are rendered by pure synchronous functions taking
  `lang="en"` and a pre-resolved names map; any async translation happens in the handler
  first. English strings must be byte-identical to the literals they replace.

## 6. Where enforcement lives

This is the load-bearing decision. The failure mode to design against is *the sixteenth
handler*: someone adds an LLM-backed command in v6.3 and forgets the quota check.

### 6.1 Rejected: metering inside `llm_transport.with_transport_retry`

`with_transport_retry` already wraps every provider network call, so hooking quota there
would give automatic coverage. It is rejected for two reasons:

1. **It cannot refuse before spending.** By the time the transport wrapper runs, the
   decision to make the call has been made. Admission control must precede work.
2. **It would require a `contextvars` billing context** to know the household and op
   class. That is precisely the hidden global state this codebase's testing story is
   built on avoiding (`CLAUDE.md`: *"No global state"*, *"callers pass `today`"*).

### 6.2 Chosen: reserve-then-commit at the handler boundary

```python
# app/billing/meter.py

OpClass = Literal["receipt", "cook", "plan", "edit", "chat", "search"]

@dataclass(frozen=True)
class QuotaSnapshot:
    receipts_used: int
    receipts_limit: int
    actions_used: int
    actions_limit: int
    per_op: Mapping[OpClass, int]
    period_end: datetime

@dataclass(frozen=True)
class Admission:
    allowed: bool
    reason: str        # "ok" | "receipts_exhausted" | "actions_exhausted"
                       # | "cost_breaker" | "subscription_expired" | "banned"
    degrade: bool      # True -> caller must use its non-LLM fallback path
    snapshot: QuotaSnapshot

def admit(session, *, household_id: int, op: OpClass, provider: str,
          now: datetime) -> Admission: ...

def commit(session, *, household_id: int, op: OpClass, provider: str,
           cost_micros: int | None, now: datetime) -> None: ...
```

Flow at every metered seam:

```
admit(...)  ->  Admission
   |  not allowed and not degrade  -> reply with the exhaustion message + /buy prompt
   |  not allowed and degrade      -> run the non-LLM fallback path
   |  allowed                      -> run the real work
commit(..., cost_micros=<what the service returned>)
```

`admit` reads and may roll the period forward; `commit` writes counters and folds the
**real** `cost_micros_usd` into the circuit breaker. Every service already returns its
cost — `IngestSummary.cost_micros_usd`, `CookSession.llm_cost_micros_usd`,
`MealPlan.cost_micros_usd`, `ShelfLifeSearchResult.cost_micros_usd` — so `commit` has an
accurate number without new plumbing.

`commit` is called even when the work fails partway, with whatever cost was actually
incurred. Spend is spend.

### 6.3 The completeness test

The sixteenth-handler risk is covered by a test rather than by cleverness, using
registries that already exist:

- `app/bot.py:168` defines `_MESSAGE_COMMANDS` as a declarative tuple of
  `(name, handler, dep_names)`, assembled from per-module `COMMANDS` tuples.
- `app/callbacks/__init__.py` computes `EXPECTED_CALLBACK_ROUTES` from `get_args(Verb)`
  and `get_args(ItemRoute)`, with a runtime `assert registry.routes == EXPECTED_CALLBACK_ROUTES`.

`tests/test_billing_coverage.py` walks both registries plus the three non-command message
registrations (reply-to-message, photo, NL text) and asserts every entry appears in
either `METERED_OPS: Mapping[str, OpClass]` or `UNMETERED: frozenset[str]`. Adding a
command without classifying it fails the suite.

This mirrors the integrity test in `tests/test_i18n.py`, which enforces placeholder parity
across languages by the same enumerate-and-assert technique.

### 6.4 The metered seams

**Metered (LLM-invoking):**

| Entry point | Op | Notes |
|---|---|---|
| photo message (`handle_photo`) | `receipt` | vision + optional refine pass |
| `/add` | `edit` | text parse |
| `/correct` and the reply-to-message handler | `edit` | text parse + sometimes web search |
| `/prefs <free text>` | `edit` | profile LLM parse — **conditional**: bare `/prefs` only renders the profile and is not metered. `admit` is called after argument parsing, on the free-text branch only. |
| `/cook` | `cook` | selection + recipe + nutrition |
| `/plan` | `plan` | composer + per-day source search |
| NL text catch-all (`handle_nl_message`) | `chat` | Agno intent classify |
| callbacks `cook_alt`, `cook_more`, `cook_adjust`, `cook_more_opts`, `fav_cook` | `cook` | re-runs recipe search |
| callback `plan_swap` | `plan` | re-searches one day |
| callbacks `freeze`, `fridge` | `search` | `resolve_storage_days` may hit web search |
| callback `item_ctext` | `edit` | free-text correction |

**Unmetered (no LLM spend):** `/start`, `/help`, `/list`, `/pantry`, `/stats`,
`/shopping`, `/favorites` (listing), `/household`, `/invite`, `/join`, `/leave`,
`/remove`, `/tz`, `/lang`, `/digest_at`, `/llm`, `/quota`, `/buy`, `/billing`, and the
pure-state callbacks (`ate`, `toss`, `snooze2`, `show_all`, `apply`, `cancel`,
`undo_receipt`, `undo_add`, `cook_like`, `cook_dislike`, `cook_save`, `cook_shop`,
`shop_done`, `item_open`, `item_list`, `item_corr`, `item_nudge`, `item_rm`,
`item_rmok`, `plan_shop`, `plan_cancel`, `help`).

**The daily digest is never metered and never gated.** It costs nothing (pure render over
`list_digest_due`) and it is the product's daily heartbeat; suppressing it for
non-payment would read as a broken bot rather than as a limit.

## 7. Data model

One Alembic migration, `0017_billing.py`. No existing table changes shape; `User` gains
one column.

```python
PlanTier  = Literal["free", "family"]
SubStatus = Literal["active", "past_due", "cancelled", "expired"]
OpClass   = Literal["receipt", "cook", "plan", "edit", "chat", "search"]
PaymentKind = Literal["subscription", "topup", "refund", "grant"]


class Subscription(SQLModel, table=True):
    household_id: int = Field(foreign_key="household.id", primary_key=True)
    tier: str = "free"
    status: str = "active"
    # Telegram's subscription identity. Required by refund_star_payment and
    # edit_user_star_subscription. None for free-tier households.
    telegram_charge_id: str | None = None
    # The telegram_id that owns the paid subscription (Stars refunds are
    # per-user, not per-household).
    payer_telegram_id: int | None = None
    # The window quota is measured over. For paid households this tracks
    # Telegram's 30-day cycle via subscription_expiration_date.
    period_start: datetime
    period_end: datetime
    seat_cap: int = 2
    created_at: datetime
    updated_at: datetime


class QuotaUsage(SQLModel, table=True):
    # One row per household per period. Counters, not a log.
    household_id: int = Field(foreign_key="household.id", primary_key=True)
    period_start: datetime = Field(primary_key=True)

    receipts_used: int = 0
    actions_used: int = 0          # authoritative weighted total

    # Raw per-op counts, for the /quota breakdown only.
    cook_used: int = 0
    plan_used: int = 0
    edit_used: int = 0
    chat_used: int = 0
    search_used: int = 0

    cost_micros_used: int = 0      # circuit-breaker input; never displayed

    # Top-ups applied to THIS period; expire with it.
    receipts_granted: int = 0
    actions_granted: int = 0
    cost_micros_granted: int = 0


class PaymentEvent(SQLModel, table=True):
    __table_args__ = (
        Index("ix_payment_household_created", "household_id", "created_at"),
    )
    id: int | None = Field(default=None, primary_key=True)
    household_id: int = Field(foreign_key="household.id", index=True)
    # Idempotency key. Telegram can redeliver successful_payment.
    telegram_charge_id: str = Field(unique=True, index=True)
    kind: str
    sku: str
    stars: int
    payer_telegram_id: int
    payload_json: str
    created_at: datetime
```

`User` gains `banned: bool = False`.

### 7.1 Why both raw counters and a weighted total

`actions_used` is stored rather than derived. Deriving it would mean re-applying the
current weight table to historical raw counts, so retuning a weight would retroactively
change how much quota a household had already consumed — potentially exhausting someone
mid-period because of a deploy. Storing the weighted total freezes the weights as they
were at spend time. The raw counters exist purely to render the breakdown.

### 7.2 Backfill

Migration `0017` creates a `Subscription` row for every existing `Household`. Existing
households are backfilled to `tier="family"`, `status="active"`, `seat_cap=10`, with
`period_start=now`, `period_end=now+30d` and `telegram_charge_id=None` — a comped paid
tier. The operator and any early users are not downgraded by the deploy that introduces
billing.

## 8. Quota policy

### 8.1 Tiers

| | Free | Family |
|---|---|---|
| Receipts / period | 5 | 100 |
| Action units / period | 30 | 300 |
| Seats | 2 | 10 |
| Cost breaker | 250 000 µUSD ($0.25) | 2 500 000 µUSD ($2.50) |
| Price | — | 500 XTR / 30 days |

### 8.2 Action weights

| Op | Units |
|---|---|
| `chat` | 1 |
| `edit` | 1 |
| `search` | 2 |
| `cook` | 10 |
| `plan` | 25 |

Receipts are counted separately and never draw from the action pool.

At Family tier, 300 units buys ~30 `/cook` runs (one a day), or ~12 `/plan` runs, or a
large volume of chat and edits — with the mix left to the household. At Free tier,
30 units buys 3 `/cook` runs: enough to understand the product.

### 8.3 Provider multiplier (actions only)

```python
PROVIDER_UNIT_MULTIPLIER = {"gemini": 1, "deepseek": 1, "openai": 3, "anthropic": 3}
```

Units consumed by an action are multiplied by the multiplier for the household member's
`llm_provider`. A household on `claude-sonnet-5` gets roughly a third as many actions as
one on `gemini-3.5-flash`, which is proportional to what those actions actually cost to
serve. This makes the existing `/llm` setting self-financing instead of a way for
customers to choose how expensive they are.

The multiplier is **not** applied to receipts — see §8.4.

### 8.4 Receipt ingest is pinned to a cost-efficient provider

Receipt ingest routes to a new deployment-level `INGEST_PROVIDER` setting (default: the
cheapest configured image-capable provider), **not** the member's `/llm` choice.

Rationale: a vision call on a premium provider costs roughly 5–7× one on a flash-class
model. At 100 receipts/period that is the difference between ~$0.30 and ~$2.00 of COGS
against a subscription netting ~$4.50 after the platform cut. Pinning it keeps "100
receipts" an honest, unqualified promise rather than one that silently shrinks based on
a setting most users will never touch.

This is a small, principled change with existing precedent: per `CLAUDE.md`, the image
selector already runs with `fallback=True` and does *not* strictly honor the user's
choice, because "a provider may legitimately lack them." v6.0 extends that from
*capability* routing to *cost* routing. `/llm` continues to control every text, cook,
plan, and translation seam, where the user's preference is real and now priced.

### 8.5 The cost circuit breaker

`cost_micros_used` accumulates the real `cost_micros_usd` from every metered op. When it
exceeds the tier's breaker, `admit` returns `allowed=False, reason="cost_breaker"` and
behaves exactly like quota exhaustion (block for receipts, degrade for everything else).

The breaker is never shown as a number — a customer cannot act on "$0.42 remaining," and
exposing it would invite arguments about pennies. `/quota` shows the counters; the breaker
only ever surfaces as an ordinary "you've reached this month's limit" message.

Expected worst case at Family tier: ~$0.30 receipts + ~$0.45 actions ≈ **$0.75**, well
inside the $2.50 breaker. The breaker exists for the tail: unusually large receipts,
pathological retries, or a future provider whose pricing moves.

> **Calibration note.** The per-op cost figures behind §8.1–8.2 are estimates. `/stats`
> already reports real text-LLM cost broken down by action type from live usage. The
> first implementation task is to read the operator's own `/stats` output and adjust the
> weights and breaker constants in `plans.py` — they are deliberately isolated in one
> pure-data module so recalibration is a constant change, not a code change.

### 8.6 Period rollover

Rollover is **lazy**, evaluated inside `admit()`: if `now >= subscription.period_end`,
advance `period_start`/`period_end` by 30 days (repeatedly, if the bot was down for
longer) and open a fresh `QuotaUsage` row before deciding. No cron job, no drift, and it
self-heals after downtime. This mirrors how `pending_service` expires its 10-minute TTLs.

For paid households, renewal also arrives as an event: `SuccessfulPayment` carries
`is_recurring=True` and `subscription_expiration_date` (Unix time). That event is
**authoritative** — it sets `period_end` from Telegram's own value, so the bot's period
never diverges from the billing period. Lazy rollover is the backstop for a missed or
undelivered update.

Top-up grants live on the `QuotaUsage` row for the period they were bought in, so they
expire with it by construction — no separate expiry job.

### 8.7 Exhaustion behavior

| Op | Behavior at zero quota |
|---|---|
| `receipt` | **Hard block.** Reply with the limit message and a `/buy` button. No non-vision path exists. |
| `cook` | Degrade: offer `/favorites` (saved recipes, re-cookable against the current pantry) instead of generating. |
| `plan` | Degrade: `heuristic_compose` — already pure Python and already the composer's failure fallback. |
| `edit` | Degrade: `ShelfLifeCache` → `shelf_life_defaults` table, no LLM parse. Item is still added, with a note that shelf life is estimated. |
| `chat` | Degrade: the tiered `/help` hint, which is what NL intent failure already falls back to. |
| `search` | Degrade: cached default (90 d frozen, 7 d fridge), per `frozen_shelf_life.py`'s existing final fallback. |
| digest | **Never gated.** |

Every degraded path already exists in the codebase; v6.0 wires quota exhaustion into the
same branches that provider failure already takes.

## 9. Payments

### 9.1 The seam

```python
# app/billing/payment.py

@dataclass(frozen=True)
class Sku:
    code: str                    # "family_monthly" | "topup_receipts_50" | "topup_actions_150"
    title: str
    description: str
    stars: int
    kind: PaymentKind
    subscription_period: int | None   # 2_592_000 for the recurring SKU, else None

class PaymentProvider(Protocol):
    async def create_checkout(self, *, sku: Sku, household_id: int) -> str: ...
    async def refund(self, *, user_id: int, charge_id: str) -> bool: ...
    async def cancel_subscription(self, *, user_id: int, charge_id: str) -> bool: ...
    async def list_transactions(self, *, offset: int, limit: int) -> list[LedgerRow]: ...
```

`StarsPaymentProvider` implements it over aiogram 3.30:

| Protocol method | Bot API call |
|---|---|
| `create_checkout` | `create_invoice_link(currency="XTR", provider_token="", prices=[LabeledPrice(...)], subscription_period=...)` |
| `refund` | `refund_star_payment(user_id, telegram_payment_charge_id)` |
| `cancel_subscription` | `edit_user_star_subscription(user_id, telegram_payment_charge_id, is_canceled=True)` |
| `list_transactions` | `get_star_transactions(offset, limit)` |

Constraints from the Bot API, encoded as validation in `plans.py`:
- Stars invoices must have `currency="XTR"`, exactly one `LabeledPrice`, and an empty
  `provider_token`.
- `subscription_period` must be exactly `2_592_000` (30 days).
- A subscription price cannot exceed `10_000` Stars.

### 9.2 SKUs

| Code | Kind | Grants | Stars |
|---|---|---|---|
| `family_monthly` | subscription | tier=`family`, seats=10, full period quota | 500 |
| `topup_receipts_50` | topup | +50 receipts, +1 250 000 µ breaker headroom | 250 |
| `topup_actions_150` | topup | +150 action units, +1 250 000 µ breaker headroom | 250 |

Top-ups raise the cost breaker proportionally. Selling quota that the breaker would then
refuse to serve is not acceptable.

### 9.3 The two payment handlers

**`pre_checkout_query` — must be answered within 10 seconds** or Telegram fails the
payment. It does only cheap, local validation: household exists, SKU code is known, user
is not banned, and (for `family_monthly`) the household is not already subscribed. No LLM
calls, no outbound HTTP, no slow queries. On any doubt it answers `ok=False` with a
human-readable reason — a declined checkout is recoverable; a timeout is not.

**`successful_payment` — must be idempotent.** Telegram can redeliver updates. The unique
index on `PaymentEvent.telegram_charge_id` is the guard: insert first, and on
`IntegrityError` treat the event as already applied and return success. Order matters —
the ledger write and the entitlement update happen in one transaction, ledger first, so a
crash between them cannot double-grant.

Renewal handling reads the payment's own fields:

| Fields | Meaning | Action |
|---|---|---|
| `is_recurring=True, is_first_recurring=True` | first charge of a new subscription | upgrade tier, set `telegram_charge_id`, set `period_end` from `subscription_expiration_date` |
| `is_recurring=True, is_first_recurring` falsy | renewal | roll period from `subscription_expiration_date`, reset counters |
| `is_recurring` falsy | one-off top-up | grant onto the current `QuotaUsage` row |

### 9.4 Refunds and cancellation

Cancellation is Telegram-native: the user manages the subscription from Telegram's own UI,
and the bot learns about it when renewal simply stops arriving — lazy rollover then finds
`period_end` passed with no new payment and transitions the subscription to `expired`,
dropping the household to free-tier limits (seat cap included; existing members over the
cap are **not** evicted, but no new members may join until the household is under cap).

Operator-initiated refunds call `refund_star_payment`, write a `refund` ledger row, and
downgrade immediately.

## 10. Registration replaces the allowlist

The single largest behavioral change is a one-function edit — the payoff of the v4.0
decision to centralize authorization.

```python
# app/handler_support.py::resolve_authorization

# before
#   allowed iff User row exists OR telegram_user_id == ALLOWED_TELEGRAM_USER_ID
# after
#   allowed iff (User row exists AND not user.banned)
#            OR first contact (anyone) -> provision User + Household + free Subscription
```

`ALLOWED_TELEGRAM_USER_ID` is **repurposed, not removed**. It becomes the operator
identity — a role it already plays for `OwnerAlerter` — joined by a new
`OPERATOR_TELEGRAM_IDS` setting (comma-separated, so a second admin can be added without
a schema change).

`provision_solo_household` gains a `Subscription` row creation alongside the `Household`,
so no code path can produce a household without an entitlement.

### 10.1 Seat caps

Enforced in `invite_service`, which gains `HouseholdFull(InviteError)`:

- `create_invite` refuses when the household is already at `seat_cap`.
- `redeem_invite` re-checks at **redemption** time and raises `HouseholdFull`.

The redemption-time check is the load-bearing one: `/invite family` issues a link with
`max_uses=None`, so a single link can otherwise admit unlimited members long after the
create-time check passed.

## 11. Operator bot

A second `Bot` + `Dispatcher` on `OPERATOR_BOT_TOKEN`, running in the **same process** as
the customer bot under `asyncio.gather`, each polling loop wrapped in its own
`run_with_restart`.

Same-process is forced, not chosen. `app/db.py` creates a file-backed SQLite engine and
Railway mounts a volume to exactly one service, so two containers cannot safely share the
database. If the operator bot is ever split out, Postgres must come first.

Authorization is a plain membership test against `OPERATOR_TELEGRAM_IDS`. The operator
bot shares no handler code with the customer bot, so there is no code path by which a
customer command could reach an operator action.

| Command | Effect |
|---|---|
| `/whois <telegram_id>` | household id, tier, status, period, usage, member roster |
| `/grant <household_id> <receipts> <actions>` | comps quota; writes a `grant` ledger row with a synthetic charge id |
| `/refund <charge_id>` | `refund_star_payment`, `refund` ledger row, immediate downgrade |
| `/ban <telegram_id>` / `/unban <telegram_id>` | sets `User.banned`; banned users fail `resolve_authorization` |
| `/revenue [30d]` | aggregates the `PaymentEvent` ledger |
| `/reconcile` | diffs the local ledger against `get_star_transactions` and reports drift |

`/reconcile` matters because the ledger is the basis for `/revenue` and refunds; drift
between it and Telegram's record is the thing you want to find early, not during a
dispute.

## 12. Datastore: stay on SQLite

Write volume is genuinely small. A household writes on the order of tens of rows per
month; a receipt scan is a handful of `INSERT`s. SQLite will comfortably hold thousands of
households at this shape. Two changes ship with v6.0:

- **Enable WAL and `busy_timeout`** in `make_engine`. The default rollback journal makes
  readers block writers; with two polling loops writing to the same file this stops being
  optional. This is a few lines in `app/db.py`.
- **Keep `app/backup.py` rotation.** Money rows are append-only, so a restore loses at
  most the tail of the ledger, which `/reconcile` can then recover from Telegram.

No raw SQL is introduced anywhere, so Postgres remains a connection-string change. The one
thing that would force the migration is needing two processes on separate machines —
which is exactly why the operator bot is co-located.

## 13. Risks and accepted trade-offs

| Risk | Disposition |
|---|---|
| **Free-tier farming** via throwaway Telegram accounts | Accepted. A free household costs ~$0.06/month to serve, so farming costs more effort than it returns. `/ban` is the lever. Phone verification is disproportionate at this stage. |
| **Cost estimates are wrong** | Mitigated by §8.5's calibration step and by isolating every constant in `plans.py`. The breaker bounds the damage while the numbers are still wrong. |
| **Chargebacks** | `SuccessfulPayment` documents that funds may be debited on a buyer chargeback, outside Telegram's control. `/reconcile` surfaces it; no automated response in v6.0. |
| **Platform cut (~30%)** | Accepted as the price of the polling-only deployment and policy compliance. The `PaymentProvider` Protocol is the escape hatch if the economics stop working. |
| **A degraded bot reads as broken** | Mitigated by making every degraded path say *why*, in the member's language, with a `/buy` button. |
| **Opening registration before the ban lever exists** | Mitigated by phasing: registration opens last (§14). |

## 14. Phasing

| Phase | Content | Independently shippable |
|---|---|---|
| **1 — Metering** | Models + migration `0017`, `plans.py`, `meter.py`, `entitlement.py`, admit/commit at every seam in §6.4, `/quota`, seat caps, WAL. Everyone on the comped `family` tier; no money moves. | Yes — and it makes the operator's own bill predictable and observable |
| **2 — Payments** | `PaymentProvider` + `StarsPaymentProvider`, `/buy`, `/billing`, pre-checkout, `successful_payment`, `ledger.py`, top-ups, tier transitions. | Yes |
| **3 — Operator bot** | Second dispatcher, the six commands, `/reconcile`, `User.banned`. | Yes |
| **4 — Open registration** | Flip `resolve_authorization`; repurpose `ALLOWED_TELEGRAM_USER_ID`; free tier becomes the default for new households. | Last, deliberately |

Phase 4 is last on purpose: the doors do not open until metering, billing, and the ban
lever all exist. Phase 1 shipped alone already pays for itself by bounding the operator's
current spend.

## 15. Internationalization

Every new customer-facing string goes through `app/i18n.py` `MESSAGES` with `en`/`zh`/
`fr`/`es` variants: the `/quota` card, exhaustion and degradation notices, the `/buy`
catalog, payment confirmations, and the seat-cap error. The existing integrity test in
`tests/test_i18n.py` enforces placeholder parity across languages.

Per the v4.1 convention, English values must be **byte-identical** to the literals they
replace, and quota card rendering stays a pure synchronous function taking `lang` plus a
pre-resolved names map — the handler does any async translation first.

Operator-bot strings are English-only and stay out of the catalog; the operator is one
person and the surface is internal.

### 15.1 The `/quota` card

```
📊 Family quota — renews Aug 27 (30 days)

🧾 Receipts      57 / 100
⚡ AI actions   133 / 300
     cook    12 × 10 = 120
     plans    0 × 25 =   0
     edits    8 ×  1 =   8
     chat     5 ×  1 =   5

Need more? → /buy
```

Free-tier households additionally get a one-line upsell naming the paid limits.

## 17. Settings added

| Env var | Default | Purpose |
|---|---|---|
| `OPERATOR_BOT_TOKEN` | — (optional) | Operator bot; when unset the operator dispatcher is not started |
| `OPERATOR_TELEGRAM_IDS` | `ALLOWED_TELEGRAM_USER_ID` | Comma-separated operator identities |
| `INGEST_PROVIDER` | first configured of `gemini` → `openai` → `anthropic` | Provider pinned for receipt ingest (§8.4). The order is cheapest-first among image-capable providers; `deepseek` is excluded because it cannot read images. Settings validation rejects an explicit value that is not image-capable, reusing `supports(provider, "image")`. |
| `BILLING_ENABLED` | `false` | Master switch; when false, `admit` always allows (lets Phase 1 ship dark) |

`BILLING_ENABLED` is what makes the phasing safe: Phase 1 can deploy with metering
recording usage but never refusing, so the constants in `plans.py` can be calibrated
against real traffic before anything is enforced.
