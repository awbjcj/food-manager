# Food Manager v5.5 — Closing the Loop

**Status:** Design approved (pending spec review)
**Date:** 2026-08-13
**Lineage:** Two deferred tracks merged into one release — the v5.2 §5 deferrals
("tonight: X" digest line, marking a day cooked, pantry decrement, the NL
"plan my week" intent) and the v5.1 §31 intent-scope deferral. The v5.2 spec
itself files the NL plan intent under "one line in the v5.1 agent's schema when
its turn comes," so the two tracks are one piece of work, not two.
**Prerequisites:** v5.1 (NL intent seam) and v5.2 (meal planning) — both shipped.
**Migration:** `0018` (additive; `0017_billing` is current head).

## 1. Goal

`/plan` currently ends at a message. The bot proposes a week and never learns
whether any of it happened, so the pantry still lists food that was eaten, the
recipe engine re-proposes last Tuesday's dish, and waste analytics measure only
what was thrown away rather than what was cooked.

v5.5 closes that loop: a planned day can be marked cooked, marking it consumes
the pantry rows it used, and the resulting record feeds recipe novelty, the
morning digest, and `/stats`. Natural language reaches the two commands it
could not previously trigger.

## 2. Locked decisions

| Decision                     | Choice                                                                                                     | Why                                                                                                                                                                                                                                                            |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Cooked → pantry              | **Confirm, then consume** — a checklist of name-matched items, pre-checked, user confirms                  | `_set_terminal` is all-or-nothing per row and v5.2 §8 deliberately kept quantity math out, so "decrement" can only mean "mark whole rows eaten." Auto-consuming would silently destroy a half-used ingredient; one tap is the honest price of correctness.      |
| Cooked record location       | **A standalone `CookedMeal` table keyed by household + recipe**, not a `MealPlanEntry` column              | Wiring `/cook` result cards later becomes a new call site rather than a migration. `source="cook"` is a legal value from day one with no writer.                                                                                                               |
| Pending-selection state      | **The same `CookedMeal` row**, via `selection_json`, finalized by `confirmed_at`                            | Telegram caps `callback_data` at 64 bytes, so a checkbox set cannot live in the payload. Reusing the row avoids a second `PendingCorrection`-style table with its own TTL sweeper.                                                                              |
| Unconfirmed rows             | **Not cooked** — every read filters `confirmed_at IS NOT NULL`                                             | An abandoned sheet is an absence of knowledge, not evidence of a skipped meal. Same posture as an unmarked day.                                                                                                                                                |
| Unmarked days                | **Stay unmarked forever** — no auto-expiry, no nudge                                                        | Recording "not cooked" would assert a fact the bot never observed. Follows v5.4's precedent of an honest truncation footnote over inferred data.                                                                                                               |
| Dedup mechanism              | **Soft novelty penalty** — a fifth `blended_score` term with a `0.05` floor                                | `affinity()` already establishes that one signal must never hard-exclude an option. A hard exclusion window would empty the candidate set on a thin pantry and then need a relaxation pass — extra machinery for a soft preference.                             |
| Dedup signal source          | **Confirmed cooks only**, not merely-proposed recipes                                                       | Punishing a dish the household never got around to making is wrong. This signal did not exist when v3.5 first deferred dedup; track 1 is what makes it available.                                                                                              |
| History surface              | **A line in `/stats`** — no `/history` command                                                              | `/favorites` already covers "re-cook that thing I liked." A new command means new callbacks and a new `/help` topic across four languages for a feature nobody has asked for twice.                                                                            |
| Cooked action placement      | **Plan card day rows only** — not the digest keyboard, not `/cook` cards                                    | Keeps the whole feature inside the existing `plan:*` stateless callback family. The digest keyboard already carries item-action buttons.                                                                                                                       |
| Digest integration           | **Informational "tonight" line only**, no button                                                            | Closes the v5.2 deferral without competing for digest keyboard room.                                                                                                                                                                                          |
| NL intent scope              | **`cook`, `plan`, `cooked`** — shopping-list intents excluded                                               | "add eggs" is genuinely ambiguous between pantry and shopping list; the other three have unambiguous surface cues.                                                                                                                                             |
| NL quota                     | **Classification charges `chat`; the dispatched action charges its own class**                              | Mirrors `handlers/meta.py:79`. Natural language must never be a cheaper door to a metered action than typing the command.                                                                                                                                      |

## 3. Non-goals (explicit; deferred)

- **Marking an ad-hoc `/cook` result as cooked.** The seam is designed for it
  (`CookedMeal.source`), but v5.5 ships no writer. Consequence, stated plainly:
  dedup and the `/stats` line see only meals that came from a `/plan`.
- **Quantity or portion math.** Consumption stays whole-row, as in v5.2 §8.
- **Shopping-list and correction NL intents.** Still deferred from v5.1.
- **A `/history` command**, plan-adherence rates, and any nudge asking whether
  yesterday's meal happened.
- **Breakfast/lunch planning, multi-week plans, calendar export.** Unchanged
  from v5.2 §8.

## 4. Data change

One new table; migration `0018`, additive, no backfill, no server defaults.

```
CookedMeal
  id              int PK
  household_id    int  FK → household.id, indexed
  source          str            # "plan" | "cook"  ("cook" has no writer in v5.5)
  plan_entry_id   int | None  FK → mealplanentry.id
  recipe_key      str  indexed   # external_id when present, else normalize(title)
  recipe_title    str            # canonical English, per the v4.1 storage rule
  cooked_on       date
  selection_json  str = "[]"     # pantry item ids currently checked
  confirmed_at    datetime | None
```

`recipe_key` is the dedup key and is household-scoped rather than plan-scoped.
`recipe_title` stores canonical English like every other dynamic name; the
render layer translates it.

## 5. The cooked flow

The **entry point** `plan:cooked:<plan_id>:<day>` joins the existing stateless
plan callback family in `app/callbacks/plan.py`, beside `plan:swap`,
`plan:shop`, and `plan:cancel`.

The **sheet's own** callbacks use a `cook:*` prefix registered as their own
group, not the `plan:*` family — deliberately, because the sheet is keyed by
`CookedMeal.id` and must outlive its plan origin when `/cook` result cards are
wired later. A plan-prefixed toggle would have to be re-keyed at that point.

Both register through the callback registry, which rejects duplicate routes at
import time (architecture-deepening Track 2 amendment).

1. **✅ Cooked** — get-or-create the unconfirmed `CookedMeal` for that entry, so
   a double tap never forks state. Initial `selection_json` is every **active**
   pantry row whose `normalized_name` appears in the recipe's ingredients — the
   exact complement of `cook/logic.py::shopping_list`, computed with the same
   `normalize()` primitive so the bot can never ask you to buy what it just
   recorded you eating. All pre-checked.
2. **Tap an item** — `cook:tog:<cooked_id>:<item_id>` toggles one id in
   `selection_json` and re-renders in place through `app/callback_dispatch.py`
   (acknowledge first, then edit, resend on any failure other than "not
   modified").
3. **Confirm** — each checked id goes through the existing
   `pantry_service.mark_eaten(session, household_id=…, item_id=…, today=…)`.
   `_set_terminal` returns `was_already` for a non-active row, so an item another
   member already marked is skipped rather than raising. `confirmed_at` is
   stamped and the sheet is replaced by a summary.
4. **Nothing used** — confirms with zero consumption. Cooked; pantry untouched.

Free action: no `admit()` call. Nothing in this flow reaches an LLM, and
charging a household to tell the bot what it ate would be perverse.

Ownership is re-derived from `household_id` on every tap rather than trusted
from the callback payload, matching `_load_owned` in every other mutation path.

## 6. Novelty scoring

New `app/cook/novelty.py`, shaped deliberately like `app/cook/affinity.py` — a
bounded read plus a pure scorer:

- `NOVELTY_WINDOW_DAYS = 21` — one constant governs both the read and the ramp,
  since a cook older than the ramp cannot affect the score.
- `list_recent_cooks(session, *, household_id, today)` → confirmed `CookedMeal`
  rows from the last `NOVELTY_WINDOW_DAYS` days.
- `novelty(recipe_key, cooks, today)` → `1.0` when the key has no confirmed cook
  in the window; otherwise `clamp(days_since / NOVELTY_WINDOW_DAYS, 0.05, 1.0)`,
  where `days_since` is measured from the **most recent** confirmed cook of that
  key. The `0.05` floor restates the affinity rule: a repeat is discouraged,
  never forbidden.

`BLEND_WEIGHTS` re-normalizes to `health 0.30 / expiry 0.30 / deliciousness 0.15
/ affinity 0.15 / novelty 0.10`, still summing to 1.0. Health and expiry keep
their weight because waste reduction is the product's reason to exist; the new
term's 0.10 comes out of the two taste terms. `blended_score` gains a
`novelty_0_1` keyword argument, consumed at both existing call sites
(`cook/service.py`, `plan_service.py`), so `/cook` and `/plan` inherit it
together.

## 7. Digest "tonight" line

`views.digest` looks up the active `MealPlan` entry dated today, resolves its
title through `translate_texts` (recipe titles are dynamic names per v4.1), and
passes it to `renderer.render_digest(..., tonight: str | None = None)`. When
`tonight` is `None` the renderer emits exactly today's bytes.

**The line never manufactures a digest.** `send_digest_once` keeps its
silent-day early return (`scheduler.py:61`), so a household with an active plan
and nothing expiring stays as quiet as it is today.

New catalog key `digest.tonight` across en/zh/fr/es.

## 8. Natural language

`NLIntent.kind` gains `cook`, `plan`, and `cooked`; one new optional field
`days: int | None` carries `/plan`'s 3–7 range.

| Intent   | Dispatches to                          | Quota                     |
| -------- | -------------------------------------- | ------------------------- |
| `cook`   | existing `run_cook_and_render`         | `admit(op="cook")` — 10   |
| `plan`   | existing `build_plan`                  | `admit(op="plan")` — 25   |
| `cooked` | today's plan entry → the §5 sheet       | free                      |

Classification continues to charge `chat` (1 unit) at `handlers/meta.py:79`; the
dispatched action then pays its own way. Refused admission degrades to the
existing exhaustion notice with its `/buy` button.

The agent instructions must draw one boundary explicitly: **`mark` concerns one
tracked pantry item ("ate the yogurt"); `cooked` concerns a planned meal ("made
tonight's dinner").** A `cooked` intent with no active plan covering today
replies with a hint rather than an error, per the standing degradation posture.
Agent failure continues to degrade to the help hint.

## 9. `/stats`

`Stats` gains `meals_cooked_count` — confirmed `CookedMeal` rows inside the
existing 30-day `/stats` window, counted by `compute_stats` alongside the other
aggregates — and the renderer gains one line under a **new** key,
`stats.meals_cooked`.

The existing `stats.cooked` key (`i18n.py:690`,
`"  Cooked: {feedback_count} (liked {liked_count})"`) counts `/cook` sessions
that received 👍/👎 feedback — a different quantity. It is left untouched:
redefining a shipped English string violates the v4.1 byte-identical rule, and
`tests/test_i18n.py` would not catch it because placeholder parity would still
pass. Two similar-looking counters is the honest outcome — one measures recipes
rated, the other meals made.

No new command and no new `/help` topic.

## 10. Internationalization

New keys across en/zh/fr/es with placeholder parity: `digest.tonight`,
`stats.meals_cooked`, the consume-sheet header and its Confirm / Nothing-used
button labels, the cooked summary, and the "no plan covers today" hint. English
values for any string replacing an existing literal must be byte-identical.
The consume sheet renders through a pure synchronous renderer taking `lang` plus
a pre-resolved names map; the handler does all translation first.

## 11. Testing

House patterns throughout: injected `session`, explicit `today`, fakes over
network, `# type: ignore[call-arg]` on `Settings()`.

- **Novelty:** never-cooked returns `1.0`; the `0.05` floor holds for a
  same-day repeat; the ramp reaches `1.0` at 21 days; `BLEND_WEIGHTS` sums to
  1.0; `blended_score` changes rank when only novelty differs.
- **Cooked flow:** get-or-create is idempotent across a double ✅ tap; toggle
  round-trips a single id; Confirm marks exactly the checked rows eaten and
  skips already-terminal rows without raising; "Nothing used" confirms with zero
  consumption; ownership is re-checked against a foreign household.
- **Confirmation boundary:** unconfirmed rows are invisible to novelty,
  `/stats`, and every read.
- **Matching:** the pre-checked set is exactly the complement of
  `shopping_list` for the same recipe and pantry.
- **Digest:** `tonight=None` renders byte-identical English; a populated line
  renders in each language; a silent day stays silent even with an active plan.
- **NL:** each new intent dispatches to its service; the `mark` / `cooked`
  boundary classifies both directions; `cooked` without a plan replies with the
  hint; `admit` denial produces the exhaustion notice for both metered intents.
- **i18n:** key completeness and placeholder parity; `stats.cooked` unchanged.
- **Migration:** `0018` in the migration suite.

## 12. Risks

| Risk                                                                | Disposition                                                                                                                                                                     |
| ------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Name matching over-selects (recipe says "onion", pantry has three)  | Accepted — every match is pre-checked but user-confirmable, which is the entire reason for the checklist.                                                                       |
| Abandoned sheets accumulate as scratch rows                          | Accepted; they are small, household-scoped, and invisible to every read. Re-tapping the same day reuses the row rather than adding one.                                          |
| Novelty suppresses a household's genuine favourite                   | Bounded by the `0.05` floor and the 21-day ramp; a weekly staple is unaffected after a week. `/favorites` re-cooks on demand, bypassing ranking entirely.                       |
| Dedup blind to ad-hoc `/cook`                                        | Known limit, stated in §3. The `CookedMeal.source` seam makes closing it additive.                                                                                              |
